# M14-c369: Sentry release matches HEAD

Measured 06.11.2026, 21:12-21:15 +07, against production
`www.kenyonexpress.co.il`. Base HEAD `86bb2595d`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c368.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `86bb2595d2ee39404e664f5c1763c5d8c14b236b`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 21:11:56 and its deployment was created at 21:12:07.
Between 21:12:29 and 21:13:09 the production alias still pointed at the
previous deployment (`1d271e473`, one commit behind). At 21:13:22 the alias
resolved to HEAD's deployment, and the client chunks were fetched after that,
between 21:13:39 and 21:14:21. That window exists after every push; it is the
build time, not a fault in the release wiring. The mismatched state was read
from deployment metadata only; the client chunk of the previous deployment
was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c368, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `86bb2595d`. The commit that records this item moves HEAD and
triggers a new production build, whose release will be that new SHA by the
same mechanism.

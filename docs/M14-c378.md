# M14-c378: Sentry release matches HEAD

Measured 07.11.2026, 13:06-13:08 +07 (06:06-06:08 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `2098e9424`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c377.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `2098e9424e73f10c9acb43f7d961820b17c8df8b`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first listing, taken while HEAD's build was running, showed the previous
deployment behind the alias.** HEAD was committed at 13:05:42 and its
deployment was created at 13:05:51. At 13:06:36 `vercel ls --prod` showed it
`Building` and the alias still resolved to `dpl_2PnQ7KdRJGuCfDDeSbnqypxYZ8XW`
(`4c4b5f9e1`, one commit behind). HEAD's deployment turned `Ready` at
13:06:59 (deployment metadata) and the alias resolved to it at 13:07:02. The
client chunks were fetched after that, between 13:07:28 and 13:08:12. Same
build window as M14-c373 through M14-c377, not a fault in the release wiring.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c377, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 52 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `2098e9424`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

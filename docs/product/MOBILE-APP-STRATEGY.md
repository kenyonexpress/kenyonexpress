## 0. "‏React Native או ‏Flutter?" נענתה, ונבנתה

הבריף מבקש מסגרת החלטה. **ההחלטה התקבלה, האפליקציה קיימת בגרסה ‏0.2.0,
ויש לה עשרה מסכים.**

| שדה | ערך |
|------|-----|
| מסגרת | ‏**‏Expo ‏+ ‏React Native ‏0.76.9** |
| ניתוב | ‏`expo-router` ‏~4.0.0 |
| ‏New Architecture | ‏`newArchEnabled: true` |
| ‏bundle id | ‏`co.il.kenyonexpress.app` (‏iOS ו-Android) |
| ‏scheme | ‏`kenyonexpress` |
| ‏Universal Links | ‏`applinks:kenyonexpress.co.il` ‏+ ‏`www` |
| ‏iPad | ‏`supportsTablet: false` |
| מצלמה | ‏`expo-camera`, עם הסבר בעברית |
| ‏push | ‏`expo-notifications` ‏+ ‏`UIBackgroundModes: remote-notification` |
| אחסון מאובטח | ‏`expo-secure-store` |

**‏React Native ולא ‏Flutter היא ההחלטה הנכונה כאן, ולא בגלל השוואת מסגרות:**
האתר הוא ‏React, המפתחים הם ‏TypeScript, וההחלטה הארכיטקטונית המרכזית
(‏§2) מחייבת ‏WebView שמדבר עם אותו קוד. ‏Flutter היה מכריח סטק שני.

## 2. ‏D10: הקופה ב-WebView, וזו ההחלטה הטובה ביותר

מ-`apps/mobile/README.md`:

> ‏**"היא לא מממשת מחדש שום מסלול כסף.** ה-checkout רץ בתוך ‏WebView על
> האתר עצמו, דרך אותה ‏`submitCheckout` ואותה ‏`beginCheckout` שהדפדפן מריץ.
> זו הסיבה שאין כאן עגלה, אין חישוב פיצול ואין קריאה ל-Cardcom."

### 2.1 מה זה מסיר

| סיכון | למה הוא נעלם |
|--------|----------------|
| שני מתמחרי עגלה שנפרדים | יש אחד |
| חישוב פיצול שונה באפליקציה | אין חישוב באפליקציה |
| ‏`platform_percent` שמצולם שונה | אותו קוד שרת |
| מסלול ‏Cardcom שני | אין |
| ‏PCI באפליקציה | אין שדות כרטיס |
| עדכון חנות בשביל תיקון תמחור | תיקון בשרת חל מיד |

**זו החלטה שחוסכת יותר ממה שהיא נראית.** מסלול כסף כפול הוא הדרך שבה
מרקטפלייס מגלה שהאפליקציה גובה סכום אחר מהאתר.

### 2.2 מה שהיא כן עולה

| עלות | חומרה |

## 4. הפער מספר 1: ‏`apps/mobile` מחוץ לכל שער

### 4.1 המצב, והוא מכוון

| מה | הראיה |
|-----|--------|
| ‏`pnpm-workspace.yaml` אינו מכיל `packages:` | התיקייה לא נוספה אליו |
| ‏`tsconfig.json` בשורש מוציא את ‏`apps` | ‏`include` |
| ‏`biome.json` מתעלם מ-`apps` | |
| **‏`pnpm test`, ‏`type-check`, ‏`lint` אינם בודקים את הקוד שם** | ‏README |

**הסיבה נמדדה ולא שוערה:** הוספת ‏`react-native` ו-`expo` לעץ אחד עם ‏Next
מכריחה את ‏pnpm לפתור מחדש את כל תלויות האתר, **כולל ה-`overrides` על
`sharp`** שקיים כדי שמייעל התמונות בכלל יעבוד. **שבירה שם היא אתר שלא נבנה.**

**ההחלטה נכונה.** הבידוד הוא הגנה.

### 4.2 מה שנשאר פתוח

**אין ‏CI לאפליקציה.** לא בשורש (בכוונה) ולא בנפרד.

```bash
cd apps/mobile
pnpm install --ignore-workspace
pnpm type-check
```

הפקודה קיימת ומתועדת. **אף אחד לא מריץ אותה בשער.**

**אפליקציה בחנות היא קוד שלא ניתן לתקן תוך דקות** (סקירת חנות), ולכן היא
דווקא צריכה שער **הדוק יותר** מהאתר, לא רופף יותר.

### 4.3 התיקון

```yaml
# .github/workflows/mobile.yml
on:
  pull_request:
    paths: ['apps/mobile/**']
jobs:
  check:
    steps:
      - run: cd apps/mobile && pnpm install --ignore-workspace && pnpm type-check
```

**עלות: קובץ אחד. תשואה: הקוד היחיד בריפו שאף שער לא רואה.**
**זו ההמלצה מספר 1 במסמך, והיא חוסמת שחרור.**

## 5. שחרור לחנויות

### 5.1 מה חסר טכנית

| # | מה | הראיה |
|---|-----|--------|
| 1 | ‏`extra.eas.projectId` | ‏**חסר.** ‏`getExpoPushTokenAsync` נכשל בלעדיו. |
| 2 | ‏`eas init` ‏+ ‏`eas build` | ‏`eas.json` קיים |
| 3 | ‏`PUSH_ENABLED=true` **בשרת** | בלעדיו הצנרת מדלגת ולא מונה ניסיון |
| 4 | ‏`EXPO_PUBLIC_SUPABASE_URL` ‏+ ‏`ANON_KEY` | ‏`.env` של האפליקציה או `extra` |
| 5 | ‏`apple-app-site-association` בדומיין | ל-Universal Links |
| 6 | ‏`assetlinks.json` | ל-App Links באנדרואיד |

**‏5 ו-6 הם קבצים שמוגשים מהאתר.** ‏`associatedDomains` מוגדר ב-`app.json`,
אבל ‏Universal Links לא יעבדו בלי הצד השרתי. **זה נשכח כמעט תמיד.**

### 5.2 דרישות החנויות

| דרישה | ‏Apple | ‏Google | מצב |
|--------|--------|---------|-----|
| מדיניות פרטיות | חובה | חובה | ‏✅ `/legal/privacy` |
| תנאי שימוש | חובה | חובה | ✅ |
| ‏Data Safety / ‏Privacy Nutrition | חובה | חובה | ❌ |
| דירוג גיל | חובה | חובה | ❌ |
| צילומי מסך | חובה | חובה | ❌ |
| מחיקת חשבון **מתוך האפליקציה** | ‏**חובה מ-2022** | חובה | ‏**❌ צריך בדיקה** |
| ‏**‏WebView לקופה** | ‏**‏§5.3** | מקובל | ⚠️ |
| הרשאת מצלמה עם הסבר | חובה | חובה | ✅ **בעברית** |

**מחיקת חשבון היא הסעיף שהכי מפיל אפליקציות בסקירה ראשונה.** ‏Apple דורשת
שאפליקציה שמאפשרת יצירת חשבון תאפשר מחיקה **מתוך האפליקציה**, לא בהפניה
לאתר. יש לוודא שהמסלול קיים.

### 5.3 ‏WebView ו-Apple

תשלום דרך ‏WebView לסחורה **פיזית או לשירות מחוץ לאפליקציה** מותר במפורש
ואינו דורש ‏In-App Purchase. ‏קופון למסעדה הוא בדיוק זה.

**מה שכן יכול לעלות בסקירה:** אפליקציה שהיא ‏WebView **בלבד** נדחית כ-
"אתר עטוף". ‏**כאן יש עשרה מסכים מקוריים ורק הקופה ב-WebView**, וזה בצד
הבטוח. ‏`supplier/scan` עם מצלמה מקורית היא הראיה החזקה ביותר לפונקציונליות
מקורית.

## 6. מערכת עיצוב

### 6.1 המצב

| | אתר | אפליקציה |
|---|------|-----------|
| גופן | ‏Heebo, ‏self-hosted | ‏? |
| צבעים | טוקנים | ‏`adaptiveIcon.backgroundColor: #f5c518` |

| רכיבים | ‏Radix ‏+ ‏Tailwind | ‏RN מקוריים |

### 6.2 ההמלצה: **לא** לבנות מערכת עיצוב משותפת

זה נשמע כמו הדבר הנכון, והוא לא:

| למה לא |
|---------|
| ‏Tailwind ו-Radix אינם רצים ב-RN |
| חבילה משותפת מחזירה את ‏`apps/mobile` לתוך ה-workspace, וזה בדיוק מה ש-§4.1 מונע |
| ‏**‏10 מסכים.** תקורת ההפשטה גדולה מהחיסכון. |
| ‏HIG ו-Material שונים מהאתר בכוונה |

**מה שכן צריך להיות משותף: ‏שלושה קבצים של ערכים בלבד**, מועתקים ולא
מיובאים:

```
apps/mobile/src/theme/
├── colors.ts      אותם ערכים כמו טוקני האתר
├── spacing.ts
└── typography.ts  Heebo, אותה סקאלה
```

**העתקה של ‏50 שורות עדיפה על חבילה משותפת ששוברת את הבידוד.**

### 6.3 ‏RTL באפליקציה

```ts
import { I18nManager } from 'react-native'
I18nManager.allowRTL(true)
I18nManager.forceRTL(true)
```

**זו הבדיקה מספר 1 באפליקציה**, ומקבילה ל-`price-bidi.spec.ts` באתר:
‏`₪` ומספר בתוך טקסט עברי נשברים ראשונים.

### 6.4 נגישות

לאתר יש ‏`a11y.spec.ts` עם ‏80 מקרים ו-axe.
‏**לאפליקציה אין שום בדיקת נגישות.**

מינימום: ‏`accessibilityLabel` לכל כפתור, יעדי מגע ‏44pt (‏`touch-targets.spec.ts`
עושה זאת באתר), וניגודיות. ‏**מרביתם ניתנים לבדיקה ידנית ב-15 דקות.**

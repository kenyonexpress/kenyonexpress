## 0. עקרונות מחייבים

1. ספק לא עולה לאוויר בלי אימייל תפעולי + אישור אדמין/בעלים.
2. לפני publish: לכל מוצר פיזי חובה `platform_percent` (דינמי, בלי ברירת מחדל). לכל קופון חובה `coupon_price_ils` מוחלט.
3. הסבר כספי לספק: מקדמת קופון שנגבית באתר **נשארת בפלטפורמה**; יתרה נגבית במזומן/בקופה בעסק בסריקה. **אין Escrow** ואין שחרור מקדמה לספק.
4. פיזי: הלקוח משלם 100% באתר; הפלטפורמה שומרת את אחוז ה-snapshot; היתרה ל-payout לפי מדיניות T+3.
5. אין עמלת 5%/10% קבועה במערכת או בחוזה התפעולי כברירת מחדל.

## 1. תהליך צירוף (end-to-end)

```
Lead / פנייה
  → איסוף מסמכים (§2)
  → בדיקת אדמין (KYC קל)
  → יצירת public.suppliers (status=pending)
  → הזמנת משתמש ל-supplier_members (Google)
  → הדרכת כסף + סורק QR (§5)
  → הגדרת platform_percent / coupon_price על מוצרים (§4)
  → מוצרים ב-draft → אישור אדמין → published
  → go-live ספק (status=active)
  → מעקב שבוע ראשון (סריקות / משלוחים)
```

| שלב | בעלים | יציאה |
|---|---|---|
| Lead | מכירות/בעלים | טופס מלא |
| KYC | אדמין | מסמכים תקינים |
| Account | אדמין | שורת supplier + member |
| Catalog | ספק + אדמין | ≥1 מוצר מאושר עם כסף תקין |
| Live | אדמין | status active + ספק בפורטל |

השעיה: אדמין יכול `suspended` → unpublish מוצרים + חסימת סורק.

### 1.1 SLA פנימי לשלבים

| שלב | יעד זמן | אם חורג |
|---|---|---|
| מענה ראשוני ל-Lead | 2 ימי עסקים | תזכורת לבעלים |
| בדיקת KYC אחרי קבלת מסמכים | 3 ימי עסקים | סטטוס pending עם סיבה |
| אישור מוצר ראשון | 2 ימי עסקים מהגשה | פידבק מפורט לספק, לא דחייה שקטה |
| go-live אחרי אישור מוצר | 1 יום עסקים | |

שדות חובה בטופס הפנייה, לפני כל שיחה:

| תחום (מסעדה / חנות / שירות) | בחירה | משפיע על קופון מול פיזי |

## 4. הגדרת `platform_percent` ומחירי קופון

### 4.1 פיזי

| כלל | פירוט |
|---|---|
| שדה | `products.platform_percent` |
| חובה | NOT NULL לפני publish (מיגרציה 050+) |
| ברירת מחדל | **אין**. האדמין/הספק (באישור) מזינים ערך פר-מוצר |
| טווח | לפי validation אדמין (למשל 0 < x ≤ 100); לא מקודד 5 |
| צילום | ב-`order_items` בזמן קנייה; שינוי אחר כך לא משכתב הזמנות ישנות |
| חשיפה ללקוח | **לא** מציגים את האחוז ב-PDP (הלקוח משלם מחיר מלא) |

### 4.2 קופון

| כלל | פירוט |
|---|---|
| שדה מחיר באתר | `products.coupon_price_ils` מוחלט |
| גבייה | מלוא הסכום ב-Cardcom באתר |
| `platform_percent` על קופון | לא משמש לפיצול מקדמה לספק (מודל סופי: 100% לפלטפורמה). יכול להישאר לדיווח פנימי בלבד או 100 ב-snapshot |
| יתרה בעסק | face − coupon_price; לא עוברת בפלטפורמה |
| תוקף | `coupon_expiry_days` / `offer_valid_until` חובה לפני publish |

### 4.3 שערי publish (אדמין)

| בדיקה | חוסם |
|---|---|
| `supplier_id` משויך | כן |
| פיזי: `platform_percent` מולא | כן |
| קופון: `coupon_price_ils > 0` ו-≤ face | כן |
| תמונה ראשית | כן (מדיניות תוכן) |
| הוראות מימוש בעברית (קופון) | כן |

## 5. הדרכת ספק (יום go-live)

צ'קליסט שיחה / PDF קצר:

1. איך נכנסים ל-`/supplier` (Google).
2. סריקת QR: חד-פעמי; מה הלקוח משלם בעסק.
3. **אין** ציפייה לקבל את מקדמת האתר מהפלטפורמה.
4. הזמנה פיזית: התראה + עדכון shipped.
5. איפה רואים יתרת payout (פיזי בלבד).
6. מי לתמיכה ב-KE (לא לשנות מחירים בלי אדמין אם נדרש אישור).

נוסח אסור בהדרכה: "Escrow", "נאמן", "נשחרר 90% אחרי סריקה" (לגבי מקדמת אתר).

## 6.1 שאלות נפוצות של ספקים (תשובות מחייבות)

| שאלה | תשובה |
|---|---|
| "מתי אני מקבל את הכסף מהקופון שנמכר באתר?" | לא מקבל. מקדמת האתר היא הכנסת הפלטפורמה. ההכנסה של הספק היא היתרה שהלקוח משלם בעסק בזמן המימוש, ישירות אליו. |
| "ולמה שווה לי?" | הקופון הוא ערוץ שיווק: הפלטפורמה מביאה לקוח משלם לדלת. את מחיר הקופון מול השווי קובעים יחד כך שהיתרה בעסק מכסה את העלות. |
| "מה עם מוצר פיזי?" | הלקוח משלם 100% באתר. הפלטפורמה מעבירה לספק את החלק שלו לפי האחוז שסוכם (payout T+3), האחוז מצולם על כל הזמנה. |
| "אפשר לשנות את האחוז אחרי שסוכם?" | כן, דרך אדמין, אבל רק להזמנות חדשות. הזמנות שכבר בוצעו נשארות על האחוז שצולם בהן. |
| "לקוח הגיע עם QR שכבר נסרק" | הסורק ידחה אותו. לא לכבד קופון שנדחה בסריקה; להפנות את הלקוח לתמיכה. |
| "לקוח רוצה החזר על קופון" | החזרים מטופלים על ידי הפלטפורמה לפי מדיניות ההחזרים, לא בקופה של העסק. |

## 7. Offboarding (עזיבה / השעיה / סגירת עסק)

הרגע המסוכן כספית: ספק עוזב כשיש **קופונים משולמים שטרם מומשו**. הלקוחות שילמו לפלטפורמה, והעסק שאמור לכבד את היתרה נעלם.

### 7.1 תהליך

```
טריגר (בקשת ספק / הפרה / סגירת עסק)
  → status=suspended: unpublish כל המוצרים, חסימת /scan
  → שליפת כל ה-vouchers במצב issued של הספק
  → החלטת בעלים לכל voucher פתוח (§7.2)
  → יישוב payout אחרון לפיזי (משלוחים שכבר יצאו)
  → status=terminated + תיעוד סיבה
```

### 7.2 טיפול בקופונים פתוחים

| מצב | פעולה |
|---|---|
| העסק ממשיך לפעול פיזית ומוכן לכבד | תיאום חלון מימוש אחרון (למשל 30 יום), הודעה ללקוחות, אחרי החלון: החזר יזום |
| העסק נסגר / מסרב לכבד | החזר מלא של `coupon_price` ששולם באתר לכל voucher פתוח, יזום על ידי הפלטפורמה |
| voucher שכבר מומש (used) | לא מטופל; העסקה הושלמה |

ההחזר הוא על מה שהלקוח שילם באתר בלבד. היתרה שהיה אמור לשלם בעסק מעולם לא נגבתה, אין מה להחזיר בה.

### 7.3 חסימות מערכת ב-offboarding

| פריט | אכיפה |
|---|---|
| מוצרים | unpublish מיידי; לא נמכרים קופונים חדשים לעסק גוסס |
| `/scan` | membership מבוטל; סריקה נחסמת |
| פורטל ספק | קריאה בלבד או חסום, לפי החלטת אדמין |
| נתונים | שורות suppliers/orders לא נמחקות (חשבונאות); רק status משתנה |

# M14-c379: Sentry release matches HEAD

Measured 07.11.2026, 14:36-14:38 +07 (07:36-07:38 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `8fb55f720`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c378.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `8fb55f720642682e63e57bd9eb7b08d840c9d110`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first listing, taken while HEAD's build was running, showed the previous
deployment behind the alias.** HEAD was committed at 14:35:19 and its
deployment was created at 14:35:28. At 14:36:02 `vercel inspect` resolved the
alias to `dpl_8XRSN8YUFQxxdQTsUVyWw7dXr9qY` (`f38d8aaad`, one commit behind)
and at 14:36:34 the listing showed HEAD's deployment `BUILDING`. HEAD's
deployment turned `READY` at 14:36:39 (deployment metadata) and the alias
resolved to it at 14:36:54. The client chunks were fetched after that, between
14:37:08 and 14:38:03. Same build window as M14-c373 through M14-c378, not a
fault in the release wiring.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c378, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 52 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `8fb55f720`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

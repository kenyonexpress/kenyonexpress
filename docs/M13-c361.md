# M13-c361: do /api/health and /api/ready return 200 with real deps?

Run 2026-11-05 on `closeout/v1-final`, base HEAD `215b044b2`.

**Answer: `/api/health` yes, in production and locally. `/api/ready`
answered with the maintenance page in production, and that was a defect.**
Under `MAINTENANCE_MODE` the proxy exempted `/api/health` but not
`/api/ready`. A deploy gate or load balancer probing readiness got
`503 text/html`, the maintenance page, so "the shop is in maintenance" looked
the same as "a dependency is down". `/api/ready` is now in the exemption list,
next to `/api/health`. This doesn't affect production until the next deploy,
and nothing was deployed.

With real dependencies locally, readiness is 200 once the local Meilisearch
placeholder is removed. With the placeholder, it is a correct 503 (see
"Meilisearch, locally" below).

## The fix

`src/lib/resilience/maintenance.ts`: `'/api/ready'` added to
`EXEMPT_PREFIXES`, with the measurement in a comment. The test now asserts
that `/api/ready` is exempt and `/api/readyz` is not, because a prefix
matches only the path itself or a child path, never a longer word.

## Meilisearch, locally: placeholder values, not a code defect

The local `.env.production` (gitignored, 23.10) contains 31 values that are
the literal string `[SENSITIVE]`, which is what a Vercel env pull leaves for
sensitive variables. `MEILISEARCH_HOST` is one of them:

```
.env.production host=[SENSITIVE] keylen=11
curl: (3) bad range in URL position 2:
[SENSITIVE]/health
```

The probe calls `[SENSITIVE]/health`, gets nothing back, and correctly reports
`down`. That is an honest 503, not a false one. Production has the real host;
an earlier measurement (14.10) found the ping answering there while searches
fell back to Postgres. The search check now runs a `limit: 1` query after the
ping, so production readiness will show the real state on the first deploy
after this one. Getting the production key locally to test it was ruled out
on purpose.

## What "real" covers on each check

| check | what it does | local result |
|---|---|---|
| database | HEAD count on `categories` (network) | ok, real |
| redis | `check_rate_limit` RPC in Postgres (network) | ok, real |
| meilisearch | `/health` plus a `limit: 1` search (network) | down: placeholder host |
| r2 | configuration only: four vars non-empty | ok, but a placeholder string also reads ok |
| cardcom | configuration only: terminal and API name set | ok, same caveat |

R2 and Cardcom are configuration-only by design: Cardcom has no side-effect-free
call (see `src/lib/health/checks.ts`). Locally, `ok` on those two means only
that a non-empty string is set. Nothing was changed here.

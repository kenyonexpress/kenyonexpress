# M14-c375: Sentry release matches HEAD

Measured 07.11.2026, 06:49-06:51 +07 (23:49-23:51 UTC on 06.11), against
production `www.kenyonexpress.co.il`. Base HEAD `72c40d926`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c374.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `72c40d9269b6681c2684aae964085ce384579b29`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 06:48:36 and its deployment was created at 06:48:46.
At 06:49:18 the production alias still pointed at the previous deployment
(`deb1ed1c9`, one commit behind). HEAD's deployment turned `Ready` at
06:49:53 (deployment metadata; observed `Ready` at 06:49:54) and the alias
resolved to it by 06:50:03. The client chunks were fetched after that,
between 06:50:53 and 06:51:35. That window exists after every push; it is
the build time, not a fault in the release wiring. Same pattern as M14-c373
and M14-c374.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c374, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `72c40d926`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

# Internationalisation

Section 61 of `~/ke-goals/SECTIONS.md`. One locale is active: `he-IL`.

## What was here before, measured

`next-intl` is a dependency, `next.config.ts` wires its plugin,
`src/i18n/routing.ts` declared `locales: ['he', 'en']`, and `messages/he.json`
and `messages/en.json` both existed with about forty keys each.

**Not one component called any of it.** Zero `useTranslations`, zero
`getTranslations`, no `NextIntlClientProvider`, and **no `middleware.ts` at
all** - so `localePrefix: 'as-needed'` routed nothing and `/en/anything` was a
404. The whole stack was scaffolding nothing called, the same shape as
`homepage_sections` in [59] and `email_suppressions` in [60].

Against that, **1,292 rendered Hebrew strings across 275 files**.

## The three pieces

### `src/lib/i18n/locales.ts` - which locales exist and which are on

An **active** locale is one a visitor can reach and that has a complete catalog.
A **prepared** locale is one the code is shaped for: it has a direction, a date
format and a catalog with the same keys, and it is used by the tests that prove
the layout switches. It is not routed.

`en` is prepared. It is the dummy locale [61] asks for, so that `dir` flipping
to `ltr` is **exercised** rather than asserted about. `i18n.test.ts` asserts
`ACTIVE_LOCALES` is exactly `['he']`, which makes turning English on a
deliberate change that fails a test until somebody updates it.

Each locale carries an `intlTag` (`he-IL`, not `he`) because a bare language
code formats dates the way `en-US` would.

An unknown code falls back to the **default locale's** direction, not to `ltr`.
An unknown code arriving at a Hebrew site is far more likely to be a typo in a
Hebrew route than a genuine English request, and guessing `ltr` would mirror the
whole page for that mistake.

### `src/lib/i18n/format.ts` - dates, numbers, percentages

130 call sites reached `toLocaleDateString`, `toLocaleString` or `Intl.*`
directly and 123 spelled `'he-IL'` inline. Several already disagreed about what
a date looks like here: some pass `{day, month: 'long', year}` and some pass
nothing and get `9.9.2026`, on adjacent pages.

**Money is re-exported, not reimplemented.** `lib/money-format.ts` is already
the one way this project renders money, and its header records what it cost to
get there: six functions called `shekels` that disagreed about whether they took
agorot or shekels, and a bidi isolate arrived at by measuring five candidates in
Chromium because `Intl`'s own `he-IL`/`ILS` output puts the shekel sign on the
**wrong side** of the digits in an RTL paragraph. A `formatCurrency` here that
called `Intl.NumberFormat` would be the seventh function and would reintroduce
that defect.

`formatRelativeTime` takes `now` as a parameter **with no default**. Reading the
clock inside a function called from a Server Component is a build error under
`cacheComponents` - the wall `lib/homepage/cms.ts` hit - so the caller that has a
clock supplies one and the ones that cannot are forced to notice.

An invalid date returns the empty string. `new Date(undefined).toLocaleDateString()`
does not throw; it returns `Invalid Date`, and this codebase would otherwise
print those two words into a receipt.

### `src/lib/i18n/messages.ts` - the typed catalog

```ts
import { t } from '@/lib/i18n/messages'

t('footer.about')        // 'אודות'
t('footer.about', 'en')  // 'About'
t('footer.abuot')        // does not compile
```

`MessageKey` is **derived from `messages/he.json` itself**, so a key that is not
in the catalog does not compile, and a key deleted from the catalog breaks every
call site at build time rather than rendering `undefined` in a footer.

**Why this is not `useTranslations`.** next-intl stays wired: when a second
locale is switched on, its routing and request config are what turn a URL
segment into a locale. What is not used yet is its **runtime**.
`getTranslations` reads the request locale, which makes the calling component
request-dependent - and under `cacheComponents` that is the difference between a
statically prerendered page and a dynamic one. The first pages it would touch
are the home page, whose hero is the LCP element and whose static output is
measured, the footer, which is in every layout, and the account nav.
`useTranslations` in a client component needs `NextIntlClientProvider`, which
serialises the whole catalog into every page's RSC payload.

So while exactly one locale is active the catalog is **compiled in** and read
synchronously. `t('nav.home')` is a property lookup: it cannot make a page
dynamic and it costs nothing. The day a second locale is routed, `t` takes its
locale from the route segment and **this file** is where that happens, not 275
components.

A missing key returns the key itself, after trying Hebrew. A visible `nav.home`
in the middle of a page is a bug report; an empty string is a gap nobody notices
until a customer asks what the blank button does.

## The ratchet

[61] asks for "no literals in components". Extracting 1,292 strings in one
change would be an unreviewable diff across most of the UI, and an automated
extraction produces `common.string_417` keys - a catalog nobody maintains and a
component nobody reads.

So `pnpm lint` runs `scripts/i18n-gate.mjs`, which counts what is left and
refuses an increase. `HEBREW_LITERAL_CEILING` only ever goes down.

| | |
| --- | --- |
| Rendered Hebrew strings, whole tree | 1,292 |
| Excluded by decision (see below) | 589 |
| **In scope** | **703** |
| Extracted by [61] | 41 (`SiteFooter` 27, `AccountNav` 14) |
| **Ceiling today** | **662** |

The gate counts exactly what `scripts/latin-copy-scan.mjs` counts, with the
script inverted: a JSX text node, a copy-bearing attribute, or a copy-bearing
object key whose value looks like a sentence rather than like code. Two callers,
one definition of "a string a customer reads", so the two gates cannot disagree
about what copy is.

### What is excluded, and why each is a decision rather than a backlog entry

**The admin panel** - 499 of the 1,292, 39% of the total. A second language
exists for **shoppers**. The operator runs this shop in Hebrew, and translating
the admin panel would double the catalog to serve nobody. If that changes it is
its own decision with its own budget.

**The legal pages** (`app/(legal)/_content/*`) - Israeli statute text and the
site's own published terms. A translated copy is a **second legally binding
document**, and which governs is then a question for a court rather than for a
developer. The pages say in their own text that the Hebrew is the original.

**The live-site fixtures** (`ke-live-*`, `hero-singlefile-data.ts`) - verbatim
records of what kenyonexpress.co.il renders, carrying measured geometry. They
are a measurement, not copy this site authors. `latin-copy-scan.mjs` already
exempts the same files for the same reason.

## How to add a language later

1. **Add the locale** to `LOCALES` in `src/lib/i18n/locales.ts` with its
   `intlTag`, `dir` and `nativeName`.
2. **Translate the catalog.** Copy `messages/he.json` to `messages/<code>.json`
   and translate the values. `i18n.test.ts` asserts key-for-key parity with
   Hebrew and refuses an empty value, so a half-finished catalog fails the
   suite rather than shipping blank buttons.
3. **Register it in `messages.ts`** - one line in `CATALOGS`.
4. **Move it from prepared to active**: add the code to `ACTIVE_LOCALES`. The
   test asserting exactly one active locale will fail; update it deliberately.
5. **Write the middleware.** There is none today. `next-intl/middleware` with
   `routing` from `src/i18n/routing.ts` is the whole file, and this is the step
   that actually makes `/<code>/...` resolve.
6. **Make `t` locale-aware at the call site.** Today every call uses the default.
   In a server component the locale comes from the route segment; in a client
   component it comes from a context. This is the step that decides between
   keeping the synchronous catalog and moving to next-intl's runtime - see the
   note above on what that costs a statically prerendered page.
7. **Set `<html lang>` and `dir` from the locale.** `localeDirection()` already
   returns it; `src/app/layout.tsx` hardcodes `he` and `rtl` today.
8. **Extract the remaining literals.** The ratchet's number is what is left.
9. **Decide about the excluded areas.** Nothing above assumes the admin panel or
   the legal text gets translated, and both decisions should be made explicitly
   rather than inherited.

## What was not done

**The middleware is not written**, so no locale prefix resolves. That is the
literal reading of "prepared but only he-IL active", and writing it would put
every route in the application through a middleware to serve one locale.

**`<html lang="he" dir="rtl">` is still hardcoded** in the root layout. Deriving
it from the locale needs the locale to come from somewhere, which is step 6.

**662 in-scope strings are still literals.** The number is measured, gated and
falling, which is the difference between a remainder and an intention.

## 2026-09-10, SECTIONS 18 (RTL-POLISH): the formatter had one caller

`src/lib/i18n/format.ts` was written to be the one place this site decides what a
date, a number and a percentage look like, and its header carries the measurement
that justified it: 130 call sites reached `toLocaleDateString`, `toLocaleString`
or `Intl.*` directly, 123 spelling `'he-IL'` inline, several already disagreeing
about what a date looks like on adjacent pages.

**Measured 2026-09-10: the module has one production consumer** -
`app/(admin)/admin/subscriptions/page.tsx` - against **142 inline `'he-IL'`
occurrences in 83 files.** Written, documented, tested, and then not adopted:
the same shape this project keeps finding, and the reason a grep for "is the
formatting centralised" answers yes while the site is formatted in 83 places.

**Not swept, and the reason is what the sweep would do.**
`toLocaleDateString('he-IL')` with no options renders `9.9.2026`;
`formatDateShort` renders `09.09.2026`. Those are different strings, and about 30
call sites take the first form, including invoices and statements a bookkeeper
files. A mechanical migration would quietly change what 80 screens display.
That is a decision per surface, with a look at each.

**Two call sites were byte-identical to `formatDate`** - `vouchers/coupon-view.ts`
and `wallet/pass-model.ts`, same locale, same three options - and those moved.
`scripts/locale-format-gate.mjs` holds the rest at a ceiling of **140**, in
`pnpm lint`, on exactly the terms `HEBREW_LITERAL_CEILING` uses: it only ever goes
down, and it refuses a run that is BELOW it without the number being lowered, so a
migration cannot land without recording itself.

**The two unmirrored icons are in components nothing imports.**
`src/components/ui/dropdown-menu.tsx` (a `ChevronRight` on a submenu trigger,

`src/components/admin/CategoryTree.tsx` (a `ChevronRight` disclosure arrow).
Measured: neither file has a single importer anywhere in `src/` - the only
references to either name are prose in comments. They are left as they are and
recorded here rather than polished, because a fix would be to a screen no visitor
and no operator can reach. They belong to the dead-code question SECTIONS 23 asks,
not to this one.

**And the `dir` gate was wrong before it was right, which is worth keeping.** Its
first version took the first `>` after `<input` as the end of the tag. In
`onChange={(e) => setEmail(e.target.value)}` that `>` is the arrow, so the element
was cut in half and the one input the gate reported was a correct input whose
`dir="ltr"` sat three lines past the cut. A gate that fails on correct code is
worse than no gate, so it tracks brace depth and quotes instead.

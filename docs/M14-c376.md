# M14-c376: Sentry release matches HEAD

Measured 07.11.2026, 09:03-09:05 +07 (02:03-02:05 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `54e035877`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c375.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `54e03587703e91a969a7bef5b2f9f49c28fd08b3`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 09:02:24 and its deployment was created at 09:02:33.
At 09:03:09 the production alias still pointed at the previous deployment
(`d1f8eb2de`, one commit behind) and HEAD's deployment was `Building`.
HEAD's deployment turned `Ready` at 09:03:38 (deployment metadata) and the
alias resolved to it by 09:03:57. The client chunks were fetched after that,
between 09:04:43 and 09:05:28. That window exists after every push; it is
the build time, not a fault in the release wiring. Same pattern as M14-c373
through M14-c375.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c375, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 52 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `54e035877`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

Measured 05.11.2026, ~04:45 +07. The server was `PORT=3311 pnpm start` (listener
PID 62794, stopped by PID afterwards), running the build in `.next` (BUILD_ID
04:42). HEAD is `0c22e8bbc`. `git diff --stat 18624c96a HEAD -- src
next.config.ts` is empty, so the build is the current code. Production answers
503 on every route under `MAINTENANCE_MODE`, so I could not measure it.

## Result

**No LTR leaks on /, /product/barbecue or /product/bar-drink at 380, 768 or
1440.** On all 9 page/width runs:

- `<html dir="rtl" lang="he">`, and `body` computes `direction: rtl`.
- 0 visible elements whose own text contains Hebrew compute `direction: ltr`.
- 0 Hebrew text elements compute `text-align: left`, or `start` under LTR.
- Horizontal overflow is 0 px (`scrollWidth - clientWidth`).

There is exactly one `dir="ltr"` on the page, and it is deliberate. It sits on
the footer newsletter email field (`src/components/layout/FooterNewsletterForm.tsx:46`,
which existed at the design tag and is frozen). An email address is Latin, so
the field is LTR while the form around it stays RTL. The comment in the code
records this decision, and the `input-dir gate` in `pnpm lint` enforces the same
rule on all 28 tel/email/url inputs. The field has no own text node, so it is
not a leak.

I made no code change.

Measured 06.11.2026, ~09:40 to 09:50 +07, against `https://www.kenyonexpress.co.il`.
This is the first M17 measured on the live site; M17-c361 ran against a local
build because production was answering 503 under `MAINTENANCE_MODE`.

The deployment behind `www` is `dpl_4ALMiiiNP2AW2P4Ad9YBzSPJQ41E` (production,

## Result

**No Hebrew text renders left-to-right on /, or on five product pages, at 380,
768 or 1440. One cosmetic exception is recorded below: the Hebrew placeholder
of the footer newsletter email field sits at the left edge of the field. The
field is in a frozen path, so I did not change it.**

On all 18 page/width loads (6 pages x 3 widths), each answering HTTP 200 with
its real `h1`:

- `<html dir="rtl" lang="he">`, and `body` computes `direction: rtl`.
- 0 visible elements whose own text contains Hebrew compute `direction: ltr`
  (89 to 197 Hebrew text elements per load).
- 0 Hebrew text elements compute `text-align: left`, or `start` under LTR.
- Horizontal overflow is 0 px (`scrollWidth - clientWidth`).

Sample: `/`, `/product/barbecue`, `/product/bar-drink`,
`/product/launch-italian-dinner-tlv`, `/product/אייפון-13`, `/product/demo-flight`
(the M15-c362 sample). No consent cookie was preset, so the consent banner was
walked too.

## What computes LTR, and why each is not a text leak

The probe is wider than the M17-c361 one. It also counts every element whose
`direction: ltr` comes from CSS and not from a `dir` attribute, and every
input whose placeholder is Hebrew while the field is LTR. That surfaced three
things. The first two are deliberate; the third is the exception.

| What | Where | Count | Text inside | Verdict |
|---|---|---|---|---|
| `span.discount_per`, `direction: ltr` from `src/styles/product-card-deals.css:193` | `/` only | 20 | `-30%`, `-44%` ... (18 distinct values, 0 with Hebrew) | Deliberate. LTR keeps the minus sign before the number; the badge renders `-30%`. |
| `a[dir="ltr"]` supplier phone link | `/product/launch-italian-dinner-tlv`, `/product/demo-flight` | 1 each | `050-0000000`, `052-4635550` | Deliberate. A phone number is Latin digits. |
| `input[type=email][dir="ltr"]`, footer newsletter | every page, from 1024 px up | 1 | Hebrew placeholder `הזן כתובת אימייל` | **Exception, see below.** |

These are the only LTR elements on the 18 loads: on `/` at 1440,
`cssLtrNonBadge` is 0 and `cssLtrWithHebrew` is 0.

The probe's raw `TOTAL leaks=60` is the 20 discount badges on each of the three
`/` loads (20 x 3), counted by the new CSS-LTR rule before I classified them.
No other counter is non-zero.

## The exception: footer newsletter placeholder

`src/components/layout/FooterNewsletterForm.tsx:46` sets `dir="ltr"` on the
email field, because a typed address is Latin. The comment in the code records
that decision. The placeholder inherits the field's direction, though, and the
placeholder is Hebrew. Measured at 1440 on `/`:

- form: `direction: rtl`, box 135 to 605 px; submit button 135 to 230; input 230 to 605.
- input: `direction: ltr`, `text-align: start`; `::placeholder` computes the same.

So the Hebrew prompt starts at the left edge of the field, next to the button,
and not at the right edge where a Hebrew reader starts. A screenshot of the
form confirms it. The word order is correct; only the alignment is LTR. A
typed address (`name@example.com`) correctly sits at the left.

Scope: the newsletter band is `hidden lg:block`, so the field is not rendered
at 380 or 768 and is visible from 1024 px up, on every page with the footer:

```
380 [{"w":0,"h":0,"hiddenBy":"div.hidden.bg-brand-secondary.text-heading.lg:block"}]
768 [{"w":0,"h":0,"hiddenBy":"div.hidden.bg-brand-secondary.text-heading.lg:block"}]
1024 [{"w":375,"h":41,"hiddenBy":null}]
1440 [{"w":375,"h":41,"hiddenBy":null}]
```

M17-c361 recorded this field as "deliberate, not a leak" because it has no own
text node. That reasoning missed the placeholder; this record corrects it.

Not fixed here: `src/components/layout` is frozen, and the file is identical
to the design tag (`git diff design-locked-2026-10-19 -- src/components/layout/FooterNewsletterForm.tsx`
is empty), so the locked design shipped this way. I could not compare against the
live-site reference the queue rules name (`ke_live_singlefile.html`, expected under `refs/`):
that file is not in the repo. Whether to keep it
or change it is Ofir's decision; the change would probably be one class on the input
(`placeholder:text-end`), which I did not test. Logged as BACKLOG #25.

  order.

  horizontal overflow and correct text direction do not prove it.
- Pages outside the sample: 77 of the 82 active product pages, and every other
  route.
- Hover, focus and open-drawer states.

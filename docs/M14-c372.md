# M14-c372: Sentry release matches HEAD

Measured 07.11.2026, 02:13-02:16 +07 (19:13-19:16 UTC on 06.11), against
production `www.kenyonexpress.co.il`. Base HEAD `5f757e7fd`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c371.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `5f757e7fd10bbcb8057a3599d3d689448999ad08`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 02:13:27 and its deployment was created at 02:13:36.
At 02:14:09 the production alias still pointed at the previous deployment
(`953d645da`, one commit behind) and HEAD's deployment was `Building`. It
turned `Ready` at 02:15:02 and the alias resolved to it at the same reading.
The client chunks were fetched after that, between 02:15:43 and 02:16:25.
That window exists after every push; it is the build time, not a fault in the
release wiring. The mismatched state was read from deployment metadata only;
the client chunk of the previous deployment was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c371, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `5f757e7fd`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

# M14-c377: Sentry release matches HEAD

Measured 07.11.2026, 11:09-11:10 +07 (04:09-04:10 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `d16d808cd`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c376.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `d16d808cd4b20db956e9b2329254196b51fb9715`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first listing, taken while HEAD's build was running, showed the previous
deployment behind the alias.** HEAD was committed at 11:08:07 and its
deployment was created at 11:08:16. At 11:09:12 `vercel ls --prod` showed it
`Building` and the alias still resolved to `dpl_5XnTTpg8odhuySYKaCJtPdz2fwc3`
(`1ad7f89d0`, one commit behind). HEAD's deployment turned `Ready` at
11:09:27 (deployment metadata) and the alias resolved to it at 11:09:41. The
client chunks were fetched after that, between 11:09:49 and 11:10:39. Same
build window as M14-c373 through M14-c376, not a fault in the release wiring.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c376, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 52 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `d16d808cd`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

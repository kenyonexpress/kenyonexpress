## Cancelled duplicate requests

Three, in 2 of the 44 loads:

```
/ @1440 (pass 1): cancelledDup=1
   cancelled-duplicate: other /_next/image?url=/images/hero/category/cute-golden-retriever-600x600.webp&w=128&q=75
/product/אייפון-13 @1440 (pass 2): cancelledDup=2
   cancelled-duplicate: other /_next/image?url=/images/products/maxresdefault-1-600x600.webp&w=640&q=75
   cancelled-duplicate: other /_next/image?url=/images/logo.webp&w=384&q=75
```

None is a console error, and no image is broken in either load. Each URL had
already answered 200 in the same load, and each answers 200 on its own:

```
$ curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download}B\n" "<hero category URL>"
200 image/jpeg 1759B
$ curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download}B\n" "<product image URL, w=640>"
200 image/jpeg 21252B
$ curl -s -o /dev/null -w "%{http_code} %{content_type} %{size_download}B\n" "<logo URL, w=384>"
200 image/webp 4046B
```

This widens what M15-c363 recorded. There it was seen only on
`/product/אייפון-13` at 380, and both URLs were candidates of the page's two
`<link rel="preload" as="image" imageSrcSet>` tags. In this run:

- It appears at 1440, and on `/`. M15-c363 had not seen it at 1440 or on any
  page other than `/product/אייפון-13`.
- The two on `/product/אייפון-13` are again candidates of those two preload tags
  (the logo's 1x / 384w, and the product image's 640w, in place of 384w at 380).
- The one on `/` is not a preload candidate. None of the six
  `<link rel="preload">` tags in the home HTML references that image. The URL is
  the 1x candidate of two `loading="lazy"` 100x100 `<img>` tags that carry the
  same `srcSet`.

So the preload tags do not account for every case.

**Not established:** why Chromium issues the second request and cancels it. No
CDP trace was taken in this run; the classification rests on the probe's rule
(aborted, and the same URL answered 200 in the same load) and on the M15-c363
trace of the same page, which showed `canceled=true` on a VeryLow-priority
request. Whether a real browser on a normal link does the same was not measured.
Per page and width the event is intermittent: each of the two loads that showed
it was clean in the other pass.

## Warnings, recorded and not fixed

"preloaded using link preload but not used within a few seconds" notice, all at
1440, none at 380, none on `/`. Per pass they split evenly over the same four
resources: three CSS chunks (`2x0yntgphzrdv.css`, `3fe0w0vs6-xwd.css`,
`3jvpruhgirjs7.css`) and `/images/logo.webp`, 10 each in pass 1 and 6 each in
pass 2. They are warnings, not errors, and the logo preload lives in
`src/app/layout.tsx`, which is frozen. The count moves between runs with load
timing (16 and 4 in M15-c362, 10 and 12 in M15-c363); 40 is the highest
recorded so far, with two product pages logging the set of four twice in one
load.

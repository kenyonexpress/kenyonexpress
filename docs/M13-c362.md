# M13-c362: do /api/health and /api/ready return 200 with real deps?

Run 2026-11-06 on `closeout/v1-final`, base HEAD `c543fba31`.

**Answer: yes, both, in production and locally.** No code change.

This is the first cycle where production `/api/ready` is a 200. In M13-c361
it answered `503 text/html` (the maintenance page). Since then maintenance was
turned off (`7cb87ea6d`) and the deploy carries both the proxy
exemption from M13-c361 and the "Meilisearch is optional" change (`546041daf`).

Three GETs each, six of six 200. `x-matched-path` shows the route handlers
answered, not the proxy.

**Recorded, not fixed: production Meilisearch is `down`.** The host and key
are set in production and the engine does not answer, so `search: "degraded"`:
search is served by Postgres, without typo tolerance or synonyms. Readiness is
a 200 on purpose (`src/lib/health/ready.ts`, `OPTIONAL`), because the shop
takes orders without the engine. Bringing the engine back is an
infrastructure task for Ofir, not a code change.

A monitor pointed at the apex gets a 308, not a 200. Point monitors at `www`
(same root cause as BACKLOG #23).

### D. Negative control: a 60-character service-role key the project rejects

```
{"ok":false,"database":"down","latency_ms":786}
/api/health HTTP 503 application/json
```

So the 200s above are measured, not unconditional: with the database
unreachable both routes answer 503 JSON, and neither leaks the upstream error.

My first attempt at this control used a 15-character key and proved something
else: the boot-time env validation rejected it ("String must contain at least
40 character(s)"), the instrumentation hook failed, and every route answered a
bare `500 Internal Server Error`. That is the env gate working as designed, and
a monitor still pages on it, but it is not the routes' own 503.

## Latency, recorded

Local `/api/ready` took 0.9s to 6.5s across nine calls, and the server logged
`db.query_slow` (threshold 1500ms) on six probe queries, the slowest a 6504ms
HEAD on `categories`. This is a laptop in +07 calling a database in Europe.
Production, in `fra1` next to the database, took 1.1s to 2.2s end to end from
here, with `latency_ms: 601` inside the handler. A monitor with a timeout
under about 5s on `/api/ready` could false-alarm; nothing was changed.

## What "real" covers on each check

Unchanged from M13-c361: `database`, `redis` (the Postgres rate limiter) and
`meilisearch` are network calls. `r2` and `cardcom` are configuration-only by
design, so `ok` there means the variables are non-empty, and locally a
placeholder string also reads `ok`.

## 1. מה רץ היום, במדויק

### 1.1 שני ה-projects

```
chromium        Desktop Chrome    כל הסוויטה, כולל מסלול הכסף
mobile-chrome   Pixel 5           כל הסוויטה חוץ מ-full-purchase-redeem
```

**‏`full-purchase-redeem.spec.ts` מוחרג ממובייל בכוונה**, כדי לחסום את זמן
ה-CI. ‏זה תיעוד של החלטה ולא פער, אבל ראה §4.2.

### 1.2 הספקים הרלוונטיים למובייל

| ‏spec | מה בודק |
|------|----------|
| `rtl-mobile.spec.ts` | ‏RTL בנייד, ‏162 מקרים |
| `rtl-three-widths.spec.ts` | ‏380 / 768 / 1440 |
| `touch-targets.spec.ts` | גודל יעד מגע |
| `layout-stability.spec.ts` | ‏CLS |
| `a11y.spec.ts` | ‏axe, ‏80 מקרים |
| `price-bidi.spec.ts` | **דו-כיווניות במחיר.** ‏₪ ומספר בתוך טקסט עברי. |
| `smoke-all-routes.spec.ts` | כל המסלולים עולים |
| `region-menu.spec.ts` | בורר אזור |

**‏`price-bidi.spec.ts` הוא הספק הכי חשוב ברשימה ולא הכי מובן מאליו.**
מחיר בעברית הוא טקסט דו-כיווני, והסימן `₪` נודד לצד הלא נכון בלי סימני
כיווניות. בנייד, שבו השורה צרה, זה נשבר ראשון.

### 1.3 שער הפיקסלים

שלוש רוחבים: **‏380, ‏768, ‏1440**. תקרה ‏11%. השער כותב שורה ל-
`docs/UI-PARITY-REPORT.md` בכל ריצה.

**המרווח האמיתי הוא כשליש אחוז, לא שלושה:**

| מסלול | רוחב | הפרש |
|--------|------|-------|
| `checkout` | 1440 | **10.71%** |
| `home` | 380 | **10.68%** |
| `cart` | 768 | **10.57%** |

**‏`home` ב-380 הוא המסלול הנייד הקרוב ביותר לתקרה.** כל שינוי חזותי בדף
הבית חייב מדידה ב-380 לפני commit.

**ארבעה מסלולים מסרבים להימדד** (‏product, ‏category, ‏products, ‏search) על
**הפרש קטלוג ולא על פריסה**: האתר החי מציג כרטיס אחד "מוצרים קשורים" ואנחנו
מציגים ארבעה או חמישה. זה לא באג נייד ואין מה לרדוף אחריו.

## 2. הפער האמיתי מספר 1: אין ‏iOS

### 2.1 מה זה אומר

‏`devices['Pixel 5']` הוא **‏Chromium בגודל של Pixel 5**. הוא לא ‏WebKit ולא
‏Safari. כלומר:

| מה לא נבדק | למה זה חשוב בישראל |
|-------------|---------------------|
| ‏Safari iOS | נתח שוק גבוה בישראל, ובמיוחד בפלח בעל כוח קנייה |
| ‏WebKit | מנוע שונה לגמרי מ-Blink |
| ‏viewport של iOS | ‏`100vh` מתחת לסרגל הכתובת |
| מקלדת ‏iOS | התנהגות שונה בפוקוס ובגלילה |
| ‏Apple Pay | לא רלוונטי היום (‏Cardcom), רלוונטי מחר |
| ‏RTL ב-WebKit | ‏**‏WebKit ו-Blink נבדלים בפרטי דו-כיווניות** |

**השורה האחרונה היא הסיכון האמיתי.** האפליקציה כולה עברית RTL, והמנוע היחיד
שנבדק הוא Blink.

### 2.2 התיקון, והוא זול

```ts
// playwright.config.ts, projects
{
  name: 'mobile-safari',
  use: { ...devices['iPhone 13'] },   // WebKit
  testIgnore: [/full-purchase-redeem\.spec\.ts/],
},
```

עלות: התקנת דפדפן ‏WebKit (‏`pnpm exec playwright install webkit`) וזמן CI.
תשואה: כיסוי של המנוע שחצי מהקהל הישראלי משתמש בו.

**זו ההמלצה בעלת התשואה הגבוהה ביותר במסמך.**

### 2.3 מה שעדיין לא ייבדק

‏WebKit של Playwright אינו ‏Safari של אייפון אמיתי. הוא קרוב מספיק כדי לתפוס
שבירות פריסה ודו-כיווניות; הוא לא יתפוס התנהגות מקלדת, ‏`100vh`, או באג
ספציפי לגרסת ‏iOS. לזה נדרש מכשיר. ‏§5.

## 3. הפער מספר 2: אין טאבלט

אין ‏project ב-768 עד 1024 בסוויטת ה-E2E. שער הפיקסלים כן מודד 768, אבל
פיקסלים אינם פונקציונליות: תפריט שנפתח לא נכון ב-iPad לא ייתפס.

```ts
{ name: 'tablet', use: { ...devices['iPad (gen 7)'] } },
```

**עדיפות בינונית.** ‏טאבלט הוא נתח קטן בקטגוריה הזו, והוא בין שני רוחבים
שכבר נבדקים.

## 4. הפער מספר 3: מסלול הכסף לא נבדק בנייד

### 4.1 המצב

`full-purchase-redeem.spec.ts` מוחרג מ-`mobile-chrome`.

### 4.2 למה זה חשוב

**הרוב המכריע של הקניות יהיה בנייד.** מסלול הכסף הוא המסלול היחיד שאסור
שיישבר, והוא היחיד שלא נבדק ברוחב שבו הוא ירוץ.

### 4.3 ההמלצה

**לא להסיר את ההחרגה** (זמן ה-CI הוא סיבה אמיתית), אלא להוסיף **ספק מובייל
ייעודי ורזה**:

```
e2e/mobile-checkout.spec.ts
  1. מוצר → עגלה, בדיקת badge
  2. עגלה → קופה, טופס נגלל ונראה
  3. שדות: מקלדת מספרית ל-טלפון, email ל-מייל
  4. כפתור התשלום נראה מעל המקלדת
  5. עצירה לפני Cardcom (mock)
```

חמישה מקרים, שנייה או שתיים כל אחד. ‏**‏5 מקרים במובייל שווים יותר מ-162
בדיקות RTL שלא נוגעות בקופה.**

## 6. ביצועים בנייד

### 6.1 המצב

‏Lighthouse Mobile **מעל 95**, נמדד ‏02.09.2026.

### 6.2 האזהרה שחייבת להיות כאן

**‏LCP ב-Lighthouse על localhost הוא סימולציה (‏Lantern) ולא מדידה.**
שיפור אמיתי של ‏2.7 שניות הופיע פעם כרעש. ‏**ציון 95 מקומי אינו ראיה
לביצועים בעולם.**

**מה שכן ראיה:** ‏`load/browse.js` מול בילד אמיתי. והוא נכשל:
**דף המוצר ‏1.2 עד 1.9 שניות חם**, מול תקציב של ‏800ms (‏`goal 19`, ‏L1).

**זה הפער האמיתי בביצועי מובייל**, והוא נמדד. ‏`docs/testing/LOAD-TESTING.md` §4.

### 6.3 תקציבים

| מדד | יעד | מצב |
|-----|-----|------|
| ‏Lighthouse Mobile | ‏> 90 | ✅ מעל 95 |
| ‏LCP שדה | ‏< 2.5s | ❌ לא נמדד בשדה |
| ‏CLS | ‏< 0.1 | ✅ `layout-stability.spec.ts` |
| ‏INP | ‏< 200ms | ❌ לא נמדד |
| **‏p95 דף מוצר** | **‏< 800ms** | ❌ **‏1.2-1.9s** |

**‏RUM אמיתי (‏`@vercel/speed-insights` כבר בתלויות) הוא הדרך היחידה לסגור
את שתי השורות ה-❌ האמצעיות.**

# M17-c363: RTL on / and a product sample, measured on production

Measured 06.11.2026, 11:39 to 12:00 +07, against `https://www.kenyonexpress.co.il`.
Read-only: no code changed.

## Result

**No Hebrew text renders left-to-right on `/` or on ten product pages, at 380,
768 or 1440. Unchanged since M17-c362, on a sample twice as wide.**

Two things to know beyond that:

- **One load showed the site's error screen instead of the product page.** In
  the first pass, `/product/מזקקת-ויסקי` at 768 rendered "משהו השתבש אצלנו"
  (the root `src/app/error.tsx` boundary) with HTTP 200. That is 1 of 24 loads
  of that page and 1 of 87 loads in this item; it did not happen again. The
  cause is not known; see "The error-screen load" below. Logged as BACKLOG #26.
- **The footer newsletter placeholder is still left-aligned** (BACKLOG #25,
  frozen file, Ofir's decision). Same measurement as M17-c362: visible at 1440
  on all 11 pages, hidden at 380 and 768.

The figures below are from the second pass (11:54 to 11:59), where all 33
loads (11 pages x 3 widths) answered HTTP 200 with their real `h1`:

- `<html dir="rtl" lang="he">`, and `body` computes `direction: rtl`, 33 of 33.
- 0 visible elements whose own text contains Hebrew compute `direction: ltr`
  (89 to 197 Hebrew text elements per load).
- 0 Hebrew text elements compute `text-align: left`, or `start` under LTR.
- 0 elements get `direction: ltr` from CSS, other than the numeric discount
  badges on `/`.
- Horizontal overflow is 0 px on every load.

The first pass gave zero on the same counters on its 32 real loads.

## The error-screen load

```

```

"משהו השתבש אצלנו" is `errorPages.errorTitle` in `messages/he.json`, rendered
by `src/app/error.tsx`, the boundary for anything thrown under the root
layout. The error screen itself is RTL (0 leaks on its 26 elements).

What I could establish:

- It was 1 of 24 loads of that page, and 1 of 87 loads in this item (two
  passes of 33, 18 reloads, 3 control loads). The 18 reloads straight after
  (6 each at 768, 380, 1440, with console capture) and the 3 loads of the
  second pass all rendered the product, with 0 console errors, 0 `pageerror`,
  0 responses of 400 or above.
- Vercel's request log has no error-level entry for that page other than a
  Node `ExperimentalWarning` on the cold start of the 380 load at 11:39:54
  (the deployment was two minutes old). The 77 rows the CLI returned for
  11:39:56 to 11:40:14, where the 768 load falls, include none for the page.
  That fits an edge cache HIT that never reached a function, but the CLI caps
  each query, so a missing row is weak evidence.
- The first pass did not record the console, so the thrown error itself was
  not captured. The probe now records console errors, `pageerror`, failed
  requests and the error screen's text, and the second pass ran in the same
  configuration (two Chromium instances in parallel) without reproducing it.

What I did not establish: what threw. `error.tsx` sends the exception to
Sentry tagged `boundary=app-error`, so the event should be there, at about
04:40 UTC on 06.11.2026. I could not read it: there is no valid Sentry token
on this machine (BACKLOG #21).

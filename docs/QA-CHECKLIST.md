# QA Checklist - בדיקה ידנית מלאה

רשימת בדיקה ידנית לכל דפי האתר, מסודרת לפי עדיפות. נבנתה מסקירת קוד בלבד (read-only).
לכל דף: מה אמור לעבוד, איך בודקים, ו-edge cases.

**מקרא עדיפויות:**
- **P0** - קריטי (הכנסה, הזדהות, אבטחה). כשל כאן חוסם משתמשים או חושף סיכון.
- **P1** - ליבה (גלישה, קנייה, ניהול תוכן). כשל פוגע קשות בחוויה.
- **P2** - משני (תצוגה, דפים סטטיים, edge cases נדירים).

**סימונים גלובליים לבדיקה בכל דף:**
- RTL: יישור טקסט, שיקוף אייקונים, תצוגת מספרים/מחירים, שדות `dir="ltr"` (טלפון, מייל, slug, SKU) בתוך הקשר RTL.
- Responsive: mobile / tablet / desktop (בדגש על breakpoints `md:` ו-`lg:`).
- מצבי loading / empty / error בכל דף שטוען נתונים.

---

## P0 - קריטי

### 1. התחברות - `/login`

**מה אמור לעבוד:** שלוש שיטות התחברות עצמאיות על אותו כרטיס - Google, אימייל+סיסמה, קישור קסם (magic link).

**איך בודקים:**
- [ ] ‏**חסום — אין משתמשי בדיקה.** התחברות תקינה עם אימייל+סיסמה מעבירה ליעד (`next`) או ל-`/`. דורש `SUPABASE_SECRET_KEY` תקין לזריעת משתמש; ראה `STATE.md`.
- [x] התחברות עם Google עובדת ומחזירה דרך `/auth/callback`. **חצי נמדד וחצי חסום, והחצי הנמדד היה באג:** ה-URL שנבנה ל-Google נשא `redirect_to=`**`undefined`**`/auth/callback` — ‏`NEXT_PUBLIC_APP_URL` הוזרק ישירות ל-template בלי fallback, ואינו ברשימת החובה של `lib/env.ts`. תוקן ל-`siteUrl()`; נמדד אחרי: `https://kenyonexpress.co.il/auth/callback?next=%2F`. המסע חזרה מ-Google עצמו לא נבדק (דורש חשבון).
- [x] "כניסה ללא סיסמה" חושף טופס magic link; שליחה מציגה "בדקו את תיבת הדואר". שניהם נמדדו: הכפתור חושף את הטופס, והשליחה החזירה "שלחנו קישור כניסה לאימייל שלך — בדקו את תיבת הדואר".
- [x] קישור "שכחתם סיסמה?" מוביל ל-`/forgot-password`. ‏`href="/forgot-password"`, והלחיצה נחתה על הדף עם הכותרת "שחזור סיסמה".
- [ ] ‏**חסום — אין משתמשי בדיקה.** מיזוג עגלת אורח. הקוד קורא `mergeGuestCart` ומוחק את `GUEST_SESSION_COOKIE` לפני ה-redirect, אבל בלי התחברות מוצלחת אי אפשר למדוד.

**Edge cases:**
- [x] פרטים שגויים -> "כתובת אימייל או סיסמה שגויים". נמדד מילה במילה.
- [ ] ‏**חסום — אין משתמשי בדיקה.** אימייל שלא אומת -> "כתובת האימייל טרם אומתה". המיפוי קיים ב-`ERROR_MAP`, ומאז הסעיף החוצה-מערכתי נפילה ממנו גם נרשמת ללוג.
- [x] שלוש שגיאות נפרדות (3 states) - ודא ששגיאה בשיטה אחת לא דולפת לאחרת. **לא דולפת.** אחרי שגיאת אימייל+סיסמה: שגיאה אחת בתוך טופס האימייל, **אפס** בבאנר העליון ו-**אפס** בטופס ה-magic link שנפתח אחריה.
- [x] **פתיחת redirect (אבטחה):** שלושת הערכים מגיעים גולמיים ל-`input[name="next"]` (`//evil.com`, `https://evil.com`, `/\evil.com`) **והשרת הוא שמנטרל**. נמדד דרך מסלול Google, שהוא היחיד שניתן להשלמה בלי חשבון: `?next=//evil.com` הפיק `redirect_to=...?next=%2F`, כלומר `/`. אותה `safeNextPath` שומרת גם על `/auth/callback`.
- [x] `?error=auth_callback_error` -> באנר אדום "הכניסה נכשלה — נסו שוב". ‏`?error=whatever_else` אינו מייצר באנר כלל.
- [x] Rate limit: 10 ניסיונות/שעה per-IP -> "יותר מדי ניסיונות כניסה". **נמדד בדיוק:** ‏10 ניסיונות החזירו "כתובת אימייל או סיסמה שגויים", וה-**11** החזיר "יותר מדי ניסיונות כניסה — נסו שוב בעוד שעה". הורץ תחת `x-forwarded-for` סינתטי כדי לא לנעול את הכתובת האמיתית לשעה — שהכותרת לבדה קובעת את הדלי היא הממצא מהסעיף החוצה-מערכתי. ה-"fails open" נשאר כתוב בקוד ולא נבדק (דורש הפלת ה-RPC).
- [x] אין בדיקת אורך סיסמה ב-login (בניגוד ל-signup). **מאושר:** סיסמה בת תו אחד נשלחה לשרת והוחזרה עם "כתובת אימייל או סיסמה שגויים", כלומר הגיעה עד Supabase.
- [x] **‏RTL (סימון גלובלי): שדות האימייל היו RTL.** ‏`you@example.com` ישב צמוד **ימין** ב-`/login` (שני השדות), `/forgot-password` ו-`/signup`, וצמוד **שמאל** ב-`/contact` — אותה כתובת בשתי צורות באותו אתר. ‏`NewsletterSignup` מנמק את הכלל בהערה ו-`ContactForm`, `SupplierLeadForm` ושדה הטלפון בהרשמה כבר מקיימים אותו. נוסף `dir="ltr"` לארבעת השדות; נמדד אחרי: `ltr` בשלושת הדפים.

### 2. הרשמה - `/signup`

**מה אמור לעבוד:** יצירת חשבון עם שם מלא, אימייל, טלפון, סיסמה + הרשמה עם Google.

**איך בודקים:**
- [ ] ‏**חסום — לא נוצרים משתמשים בפרודקשן.** הרשמה תקינה -> מעבר ל-`/signup/confirm`. אין סביבת Supabase נפרדת כאן, ולכן כל הרשמה "לבדיקה" היא שורה אמיתית ב-auth של הפרודקשן שתופיע ב-`/admin/users` ותקבל מייל אימות. **כל שאר הסעיף נמדד בלי ליצור אף משתמש**, כי zod דוחה לפני `supabase.auth.signUp`.
- [ ] ‏**חסום, אותה סיבה.** ‏`full_name` ו-`phone` נשמרים כ-metadata של המשתמש. הקוד מעביר את שניהם ב-`options.data`.

**Edge cases:**
- [x] אימות טלפון ישראלי: ארבעת הפורמטים עוברים ו-`123` נדחה עם "מספר טלפון ישראלי לא תקין (לדוגמה: 050-1234567)" — נמדד בדפדפן. שלושה מהארבעה כבר היו בטסטים; `972521234567` (בלי `+`) לא היה, ונוסף.
- [x] סיסמה: מינימום 8 תווים **וגם** לפחות ספרה אחת. **נמדד:** ‏`abcdefgh` עבר את HTML5 (`minLength={8}`) ונדחה בשרת עם "הסיסמה חייבת להכיל לפחות ספרה אחת".
- [x] שם מלא של תו אחד / רווחים בלבד -> נכשל (min 2 אחרי trim). **‏"אחרי trim" היה בדיוק מה שלא קרה — זה היה באג.** הסכימה נכתבה `.min(2).trim()`, ו-zod מפעיל שרשרת לפי הסדר: האורך נמדד על המחרוזת הגולמית והחתוך רק אחר כך. שני רווחים הם שני תווים, ולכן `"  "` **עבר** ונשמר כ-`""`, ו-`" a "` עבר ונשמר כ-`"a"` — חשבון עם שם ריק, מטופס שהכלל שלו אומר שני תווים. השדה הוא `type="text"` והדפדפן מוסר את הרווחים כמות שהם (נמדד: ערך ה-FormData היה `"  "`), בניגוד לשדות האימייל שלידו שהדפדפן כן מקצץ. תוקן ל-`.trim().min(2)`, **הסדר ששתי העתקות אחרות של אותו שדה כבר משתמשות בו** (`validations/account.ts`, `validations/checkout.ts`). נמדד אחרי בדפדפן: נדחה.
- [ ] ‏**חסום — לא נוצרים משתמשים בפרודקשן.** אימייל כבר רשום -> "כתובת האימייל כבר רשומה". המיפוי קיים ב-`ERROR_MAP`. בדיקה כלשהי כאן מחייבת או יצירת משתמש אמיתי או שימוש בכתובת של אדם אמיתי שתקבל מייל; שתיהן נדחו.
- [x] רק שגיאת ה-zod הראשונה מוצגת - בדוק כל שדה בנפרד. **נמדד:** טופס עם שם, טלפון וסיסמה פסולים בו-זמנית החזיר **רק** "שם מלא חייב להכיל לפחות 2 תווים".
- [x] Rate limit: 5 הרשמות/שעה per-IP. **נמדד בדיוק:** חמש שליחות פסולות קיבלו את שגיאת הוולידציה, ה-**6** קיבלה "יותר מדי ניסיונות הרשמה — נסו שוב בעוד שעה". הבדיקה נעשית **לפני** ה-zod, ולכן אפשר למצות את המכסה בלי ליצור אף משתמש; הורץ תחת `x-forwarded-for` סינתטי.
- [x] **‏RTL: שדה האימייל היה RTL** (ראה סעיף 1). נוסף `dir="ltr"`; שדה הטלפון כאן כבר היה תקין.

### 3. שכחתי סיסמה - `/forgot-password`

**איך בודקים:**
- [x] שליחה -> הטופס מוחלף בהודעה ירוקה "שלחנו לך קישור לאיפוס הסיסמה — בדקו את תיבת הדואר". נמדד: ההודעה מופיעה **והטופס נעלם** (שדה האימייל אינו קיים יותר ב-DOM).
- [x] קישור האיפוס במייל מצביע ל-`/auth/callback?next=/reset-password`. **אומת בקוד ובטסט**, לא במייל עצמו: זה ה-`redirectTo` שמועבר ל-`resetPasswordForEmail`, ו-`auth-redirect.test.ts` מקבע את שלושת הנתיבים. הכתובת עצמה תוקנה בסעיף 1 (הייתה `undefined/auth/callback`).

**Edge cases:**
- [x] **אבטחה (user enumeration):** אין דליפה. ‏`passwordResetResult` **מתעלם מהארגומנט שלו לחלוטין** ומחזיר תמיד את אותו אובייקט הצלחה, וגם סירוב מכסת-הכתובת מחזיר אותו. נמדד: חמש כתובות שאינן קיימות קיבלו את אותה הודעה ירוקה מילה במילה. **מה שלא נבדק:** כתובת שכן קיימת — זה שולח מייל אמיתי לאדם אמיתי.
- [x] אחרי הצלחה הטופס נעלם ולא ניתן לשלוח שוב בלי רענון. **נמדד, וזו התנהגות רצויה כאן:** במקום הטופס מוצג קישור "חזרה לכניסה", והמצב מתאפס ברענון. בלי זה, לחיצה כפולה על "שלחו" הייתה שורפת שתיים מתוך חמש מכסות הכתובת.
- [x] Rate limit: 5/שעה. **נמדד בדיוק:** חמש שליחות עברו, ה-**6** החזירה "יותר מדי ניסיונות — נסו שוב בעוד שעה" **והטופס נשאר על המסך**. שים לב שיש **שתי** מכסות: `reset:<ip>` ו-`reset-address:<email>`, והשנייה מחזירה בכוונה את הודעת ההצלחה כדי לא להסגיר קיום חשבון.

### 4. איפוס סיסמה - `/reset-password`

**איך בודקים:**
- [ ] ‏**חסום — אין משתמשי בדיקה.** הגעה דרך קישור מייל תקין -> סיסמה חדשה -> ניתוב ל-`/`.

**Edge cases:**
- [x] **כניסה ישירה ל-`/reset-password` בלי session שחזור** -> העדכון נכשל. **מוצגת שגיאה ולא מסך שבור, אבל השגיאה הייתה הלא נכונה.** ‏`updateUser` מורשה על ידי session השחזור שהקישור פותח, ולכן **קישור שפג, שכבר נוצל, או ביקור ישיר — כולם אותו מקרה**, והוא היחיד שבו הדף נכשל אצל לקוח אמיתי. ההודעה הייתה "אירעה שגיאה, נסו שוב": נכונה, חסרת תועלת, **ובדף שאין בו שום קישור אחר** — מבוי סתום. **המחרוזת נקראה מהלוג ולא נוחשה:** תיקון "מיפוי שגיאות" מהסעיף החוצה-מערכתי כתב `auth.error_unmapped … reason: "Auth session missing!"`, וזה השימוש הראשון שלו. עכשיו: "קישור האיפוס פג או שכבר נעשה בו שימוש — בקשו קישור חדש", **ובמצב שגיאה בלבד** מוצג קישור ל-`/forgot-password`. נמדד אחרי: ההודעה החדשה, והקישור נוחת על `/forgot-password`.
- [x] קישור פג/מנוצל -> העדכון נכשל. **אותו מקרה בדיוק** (אין session), ולכן אותה הודעה חדשה.
- [x] סיסמאות לא תואמות -> "הסיסמאות אינן תואמות". נמדד מילה במילה.
- [x] אין קישור "חזרה לכניסה" בדף הזה. **נכון, ונשאר נכון במצב הרגיל** (0 קישורים). הקישור היחיד שנוסף מופיע רק אחרי שגיאה ומצביע ל-`/forgot-password`, כי במצב הזה בקשת קישור חדש היא הצעד הבא ולא כניסה.

### 5. Callback הזדהות - `/auth/callback`

**מה אמור לעבוד:** מטפל ב-OAuth, magic link, ואיפוס סיסמה. מחליף `code` ל-session.

**Edge cases:**
- [x] Google OAuth: `next` שורד את המעבר דרך Google ונוחת בדף הנכון. **הרגל היוצאת נמדדה** בסעיף 1 (‏`?next=//evil.com` הפך ל-`next=%2F` בתוך ה-URL של Google); **הרגל החוזרת דורשת חשבון ולא נבדקה.** נוסף `route.test.ts` שמקבע את שתיהן מול exchange מדומה: קוד תקין נוחת על `/account/orders`, ושלושת הערכים העוינים נוחתים על `/` באותו origin.
- [x] קוד לא תקין/פג/מנוצל -> ניתוב ל-`/login?error=auth_callback_error`. נמדד: `307` לשם.
- [x] היעדר `code` (כניסה ישירה) -> אותו ניתוב בדיוק. נמדד גם עבור `?code=` ריק.
- [x] **‏`next` נזרק בכשל, וזה תוקן.** לקוח שהקוד שלו פג — רענון אחד של magic link, מעבר איטי דרך Google — התחבר שוב **ונחת בדף הבית במקום בדף שאליו ניסה להגיע**, בלי שום רמז למה. עכשיו `?code=bogus&next=/checkout/return` מנתב ל-`/login?error=auth_callback_error&next=%2Fcheckout%2Freturn`, ו-`LoginForm` כבר משחיל את `next` לשלושת הטפסים שלו. **הערך העוין אינו נוסע אפילו כפרמטר:** ‏`safeNextPath` מכווץ אותו ל-`/`, ו-`/` נשמט כדי שכתובת הכשל החשופה תישאר כפי שהייתה. נמדד לשלושת הערכים.
- [ ] ‏**חסום — דורש קוד תקין.** מיזוג עגלת אורח קורה גם כאן. הקוד קורא `mergeGuestCart`, אחריו `linkAnalyticsIdentity` **לפני** מחיקת ה-cookie (זה הרגע האחרון ששני המזהים ידועים), ואז מוחק.
- [x] **‏`NEXT_PUBLIC_APP_URL` נכון בכל סביבה** - ערך שגוי שובר את כל ה-OAuth/magic/reset. **השורה הזאת צדקה, וזה היה בדיוק הבאג של סעיף 1:** המשתנה הוזרק גולמי לשלושת ה-redirect ואינו ברשימת החובה של `lib/env.ts`, ולכן "ערך שגוי" התגלה כ-**היעדר ערך** שהופק כמחרוזת `undefined`. עבר ל-`siteUrl()` עם נפילה לדומיין הקנוני, ו-`auth-redirect.test.ts` אוסר קריאה גולמית בכל `src/`.

### 6. Checkout - `/checkout`

> הערה: קבצי התשלום עצמם (`src/lib/payments/`, `src/server/actions/payments/`) בעבודה ב-session אחר. הבדיקות כאן ברמת הדף בלבד.

**מה אמור לעבוד:** טופס תשלום עם כתובת (אם נדרש), ארנק, קופון, תנאים, ושמירת כרטיס.

> ‏**איך נמדד:** דפדפן חי חסום כאן. העגלה, קריאת הכתובת ויתרת הארנק כולן עוברות
> ב-admin client, ו-`SUPABASE_SECRET_KEY` המקומי הוא מפתח ה-demo (`iss=supabase-demo`)
> שהפרויקט המאורח דוחה — אותו חסם של סעיפים 16-31. לכן `/checkout` עונה בדיוק
> את מה שעגלה ריקה מזכה בו, וזה בעצמו ה-edge case הראשון. השאר נמדד ברינדור
> אמיתי של `CheckoutForm` (‏`checkout-form-contract.test.tsx`,
> ‏`saved-address-step-gate.test.tsx`).

**איך בודקים:**

- [x] **Rate-limit keys** per-IP; מאחורי proxy נעשה שימוש ב-`x-forwarded-for` - IP משותף/NAT עלול להגביל כמה משתמשים יחד. **נמדד, והממצא חמור יותר ממה שהשורה מתארת.** שלוש בקשות ל-`/api/search` עם ערכי `x-forwarded-for` שונים יצרו **שלוש שורות נפרדות** ב-`rate_limits`. כלומר בלי proxy שדורס את הכותרת, כל מגבלה מבוססת-IP באתר עוקפת בכותרת אחת — **ולהפך: אפשר לשרוף את המכסה של מישהו אחר.** בפרודקשן Vercel כותב את הכותרת, וזו ההנחה שמחזיקה את הכל; היא נכתבה עכשיו במפורש ב-`rate-limit.ts` ונרשמה כשאלה 14. **לא שונתה**, כי אי אפשר למדוד את התנהגות Vercel מהמחשב הזה.

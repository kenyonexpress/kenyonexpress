# M14-c364: Sentry release matches HEAD

Measured 06.11.2026, 13:11-13:15 +07, against production
`www.kenyonexpress.co.il`. Base HEAD `0b39e15d5`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c363.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `0b39e15d58b3f81cd57cb49357c87682b0f7ced7`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 13:11:20 and its deployment was created at 13:11:32. At
13:12:39 the production alias still pointed at the previous deployment
(`584ff54f0`, one commit behind). At 13:12:49 the live client chunk already
carried HEAD's SHA, and at 13:14:05 the alias resolved to HEAD's deployment.
That window exists after every push; it is the build time, not a fault in the
release wiring. The mismatched state was read from deployment metadata only;
the client chunk of the previous deployment was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c363, M14-c362, M14-c361,
M14-c111 and BACKLOG #21. Events carry the right `release` string, but Sentry
has no release entity and no source maps, so production stack traces stay
minified. The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in
Vercel Production with the `project:releases` and `org:read` scopes, created
in the Sentry UI. The variable in Vercel is 51 days old. That gap does not
affect this item's check, which compares the tag against HEAD.

The match is for `0b39e15d5`. The commit that records this item moves HEAD and
triggers a new production build, whose release will be that new SHA by the
same mechanism.

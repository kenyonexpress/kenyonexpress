# M14-c365: Sentry release matches HEAD

Measured 06.11.2026, 14:51-14:54 +07, against production
`www.kenyonexpress.co.il`. Base HEAD `a656cb4f4`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c364.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `a656cb4f4b39e3dbe609d30983f3b37572ab2809`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 14:50:35 and its deployment was created at 14:50:44. At
14:51:35 the production alias still pointed at the previous deployment
(`360a04894`, one commit behind). At 14:51:50 the alias resolved to HEAD's
deployment, and the client chunks were fetched after that, between 14:52:14
and 14:53:00. That window exists after every push; it is the build time, not
a fault in the release wiring. The mismatched state was read from deployment
metadata only; the client chunk of the previous deployment was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c364, M14-c363, M14-c362,
M14-c361, M14-c111 and BACKLOG #21. Events carry the right `release` string,
but Sentry has no release entity and no source maps, so production stack
traces stay minified. The fix is unchanged and is Ofir's: a new
`SENTRY_AUTH_TOKEN` in Vercel Production with the `project:releases` and
`org:read` scopes, created in the Sentry UI. The variable in Vercel is 51 days
old. That gap does not affect this item's check, which compares the tag
against HEAD.

The match is for `a656cb4f4`. The commit that records this item moves HEAD and
triggers a new production build, whose release will be that new SHA by the
same mechanism.

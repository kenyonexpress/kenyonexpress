# M14-c363: Sentry release matches HEAD

Measured 06.11.2026, 11:00-11:04 +07, against production
`www.kenyonexpress.co.il`. Base HEAD `921bd1c33`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c362.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `921bd1c33db338e286f9d731475718990c7329a7`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading did not match, for about 90 seconds.** At 11:00:00 the
production alias still pointed at the previous deployment (`6d2f8376e`, one
commit behind), because HEAD had been pushed at 10:59:20 and its build was
running. At 11:01:34 the alias had moved to HEAD's deployment and the second
reading matched. That window exists after every push; it is the build time,
not a fault in the release wiring. Both readings are in the proof below.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c362, M14-c361, M14-c111 and
BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `921bd1c33`. The commit that records this item moves HEAD and
triggers a new production build, whose release will be that new SHA by the
same mechanism.

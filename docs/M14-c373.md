# M14-c373: Sentry release matches HEAD

Measured 07.11.2026, 03:44-03:46 +07 (20:44-20:46 UTC on 06.11), against
production `www.kenyonexpress.co.il`. Base HEAD `7e26e6921`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c372.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `7e26e6921a4b355db4c33b85a5e8caea7bf186e6`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 03:43:26 and its deployment was created at 03:43:35.
At 03:44:18 the production alias still pointed at the previous deployment
(`e4d9ed616`, one commit behind) and HEAD's deployment was `Building`. It
turned `Ready` at 03:44:44 (deployment metadata; observed at 03:44:56) and the
alias resolved to it at 03:44:59. The client chunks were fetched after that,
between 03:45:25 and 03:46:03. That window exists after every push; it is the
build time, not a fault in the release wiring. The mismatched state was read
from deployment metadata only; the client chunk of the previous deployment was
not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c372, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `7e26e6921`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

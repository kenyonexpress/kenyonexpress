## Method

1. The ledger can't answer this. Production's `supabase_migrations.schema_migrations`
   holds 237 versions, max `20261102150200`, and its names reuse the same
   numbers for different content (`184_carts_one_row_per_owner`,
   `192_notification_history`, `232`-`234`, and so on). So the scan checks
   objects instead.
2. A parser (`/tmp/m10/scan.mjs`, not committed) strips comments from each
   `NNN_*.sql` and pulls out every object the file creates or drops: tables,
   `ADD COLUMN`/`DROP COLUMN`, functions, indexes (`DROP INDEX` means it should be
   gone), policies, triggers, views, types, enum values and `cron.schedule`
   job names. That gave **71 files and 447 objects**, which went into one
   `VALUES` query checked against `pg_class`, `information_schema.columns`,
   `pg_proc`, `pg_policies`, `pg_trigger`, `pg_type`/`pg_enum` and `cron.job`.
3. Thirteen files create no named object (grants, `ALTER FUNCTION ... SET
   search_path`, `ALTER POLICY`, CHECK rewrites, data seeds). Each one got a
   targeted check, listed below.
4. A file that only does `CREATE OR REPLACE FUNCTION` shows as present whether
   or not its body landed. 218 is one of these, so its body was read with
   `pg_get_functiondef`.

Known parser noise: in 184, `column:public.if` and `table:public` come from
`format()` strings in a `DO` block. Also, `set_updated_at` and other shared
trigger functions count as present for every file that recreates them. This
is why many "not applied" files score 1/N rather than 0/N.

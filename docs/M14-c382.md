# M14-c382: Sentry release matches HEAD

Measured 07.11.2026, 19:33-19:36 +07 (12:33-12:36 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `097e3ffb0`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c381.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `097e3ffb0cadb5a1deaea5a86ad9d2a6906853e3`, and the live
client bundle has that SHA baked in as its Sentry release.

**HEAD's deployment was still building at the first listing.** HEAD was
committed at 19:33:20 and its deployment was created at 19:33:29. At 19:34:02
the listing showed it `BUILDING`; it turned `READY` at 19:34:28 (deployment
metadata) and at 19:34:38 the alias resolved to it. The client chunks were
fetched after that, between 19:34:54 and 19:35:35. Same build window as
M14-c373 through M14-c381, not a fault in the release wiring.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c381, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 52 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `097e3ffb0`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

# M14-c374: Sentry release matches HEAD

Measured 07.11.2026, 05:14-05:16 +07 (22:14-22:16 UTC on 06.11), against
production `www.kenyonexpress.co.il`. Base HEAD `ff4da142d`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c373.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `ff4da142da7d43c699e140c57e1ab0ae9139161d`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 05:13:43 and its deployment was created at 05:13:54.
At 05:14:24 the production alias still pointed at the previous deployment
(`8eaccb9d5`, one commit behind) and HEAD's deployment was `Building`. It
turned `Ready` at 05:15:04 (deployment metadata; observed at 05:15:09) and the
alias resolved to it in the same second. The client chunks were fetched after
that, between 05:15:28 and 05:16:10. That window exists after every push; it
is the build time, not a fault in the release wiring. Same pattern as
M14-c373.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c373, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `ff4da142d`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

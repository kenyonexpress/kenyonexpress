# M14-c370: Sentry release matches HEAD

Measured 06.11.2026, 22:46-22:49 +07 (15:46-15:49 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `d211701c3`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c369.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `d211701c3d827f0bc95d1050a847e794d9dbd59d`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 22:45:44 and its deployment was created at 22:45:58.
At 22:46:15 the production alias still pointed at the previous deployment
(`84438d7be`, one commit behind). At 22:47:17 the alias resolved to HEAD's
deployment, and the client chunks were fetched after that, between 22:47:29
and 22:48:10. That window exists after every push; it is the build time, not
a fault in the release wiring. The mismatched state was read from deployment
metadata only; the client chunk of the previous deployment was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c369, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `d211701c3`. The commit that records this item moves HEAD and
triggers a new production build, whose release will be that new SHA by the
same mechanism.

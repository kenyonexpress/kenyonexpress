# M14-c371: Sentry release matches HEAD

Measured 07.11.2026, 00:34-00:37 +07 (17:34-17:37 UTC on 06.11), against
production `www.kenyonexpress.co.il`. Base HEAD `f835166115`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c370.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `f835166115715cbfdfefed47aa1814a8ef3ea86e`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was finishing, did not match.**
HEAD was committed at 00:34:13 and its deployment was created at 00:34:22.
At 00:34:58 the production alias still pointed at the previous deployment
(`10f1de0a5`, one commit behind). At 00:35:44 the alias resolved to HEAD's
deployment, and the client chunks were fetched after that, between 00:36:13
and 00:36:49. That window exists after every push; it is the build time, not
a fault in the release wiring. The mismatched state was read from deployment
metadata only; the client chunk of the previous deployment was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c370, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 51 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `f835166115`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.

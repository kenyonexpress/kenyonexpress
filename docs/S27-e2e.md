## Defects found and fixed on the way

Runs 1 to 14 were red or only partly green. Each red was read, not retried.

1. **Customer cancellation could not work in production.** `refund_requests`
   did not exist (PostgREST `PGRST205`), so `requestRefund` could only answer
   its "table missing" sentence. The table lives in `202_fraud_abuse.sql`,
   never applied, which also carries fraud scoring and disputes. New
   `migrations/pending/261_refund_requests.sql` is section 3 of 202 verbatim,
   all idempotent, so 202 later re-runs it as a no-op. Rehearsed in a
   transaction that raises at the end, then applied:

   ```
   rehearsal: ERROR: P0001: REHEARSAL OK: 12 cols, triggers=refund_request_cap,set_updated_at, policies=2
   apply:     supabase db query --linked -f migrations/pending/261_refund_requests.sql  ->  "rows": []
   after:     GET /rest/v1/refund_requests (service)  ->  200 []
   grants:    anon SELECT; authenticated REFERENCES,SELECT,TRIGGER,UPDATE; service_role all
   anon read: 200 []            (RLS: no anon policy)
   anon insert: 401 42501       (INSERT revoked)
   ```

2. **The mock payment provider failed on any multi-instance deploy.** Its
   deals lived in a per-process `Map`; the checkout created the deal on one
   Vercel function instance, the frame-return verified on another, found
   nothing, and the order went to `/checkout/failed` with the payment `failed`
   (run 5, order `35b5e2f7`). A local `next start` is one process, so no local
   run ever saw it, and every preview money flow was a coin toss. The mock's
   low-profile id now carries the amount and the save-card flag, and
   `verifyLowProfile` rebuilds the deal from it when the map misses.
   `src/lib/payments/mock-cardcom.ts`, four tests in `mock-cardcom.test.ts`.
   Mock only; the real provider asks Cardcom.

3. **A coupon-only order was stamped with the customer's home address.** The
   checkout form posts the saved `address_id` whenever the customer has one,
   and the action kept it for a cart that needs no address (run 13: a gift
   coupon order with `address_id 17790c88`). Shipping address is for physical
   products only. `runSubmitCheckout` now drops `address_id` when
   `needs_address` is not `true`; journey 3 asserts it is null.

4. **Turnstile refusals were silent.** `verifyTurnstile` returned the codes and
   logged nothing, so a key mismatch and a bot looked identical in the logs.
   It now logs `turnstile.refused` with the codes.

Test-side only (no product change): the shared `signInWithEmail` and
`walkCheckoutToPayment` press the button before the Turnstile widget has
written its token, which local runs never meet because they have no key pair.
The spec waits for the token immediately before each press, and for the
checkout's Suspense shell (it carries its own `accept_terms` box) to be gone.

## Left as they are

- The `s27-e2e` branch and its branch-scoped env stay, so the preview can be
  rebuilt and the spec re-run. They reach nothing outside that branch.
- Preview has two non-branch `TURNSTILE_SECRET_KEY` entries and two site keys
  (one real, one test). Not touched: the values are `sensitive` and cannot be
  read back, so a delete is not reversible.
- `checkout.guest_contact_save_failed` (`profiles_email_key`) fires when a
  guest reuses an email that already has a profile. Seen once on a probe that
  reused its address; the order itself completed. Logged, not in scope.
- The admin refund (money back) is not part of this run: the admin fixture
  cannot sign in headless (MFA). Journey 4 proves the customer's request lands;
  `e2e/admin-refund.spec.ts` covers the refund itself locally.

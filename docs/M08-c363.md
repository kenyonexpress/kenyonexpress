## Live performance

Devtools medians fell from 95 to 66 on `/` and from 84 to 69 on the product page. What the data shows:

| | M08-c362 | M08-c363 |
|---|---|---|
| `/` requests, transfer | 97-99, 747 kB | 96-98, 740-749 kB |
| product requests, transfer | 93-95, 658-665 kB | 94-95, 687-692 kB (the four related images now load) |
| TBT, devtools runs | at most 109 ms | at most 113 ms |
| CLS | at most 0.003 | at most 0.003 |
| Document server response | 291-302 ms | 289-325 ms in four runs, 456 and 681 ms in two `/` runs |

So the page is the same weight and the main thread is as quiet as before. The loss is in FCP and LCP (4.3-6.9 s in five of the six runs, against 2.3-5.1 s). In the LCP breakdown, time to first byte under throttling was 2.4-2.5 s on `/` and 1.3-2.0 s on the product page, and loading the LCP image took 1.0-3.4 s.

The link from this machine was slow at the time, measured right after the runs with no throttling:

```
$ curl https://www.kenyonexpress.co.il/   (5 fetches)             ttfb 0.97-2.09 s, total 6.5-16.2 s
$ curl --compressed https://www.kenyonexpress.co.il/ (3 fetches)  68 kB, ttfb 0.97-1.71 s, total 1.5-3.0 s
$ curl --compressed https://www.cloudflare.com/ (2 fetches)       ttfb 0.83-1.18 s   (unrelated site, same link)
```

About one second before the first byte on an unrelated site says the path (VPN) carries much of the delay. It does not prove all of it: two of the three `/` devtools runs also reported a document server response of 456 and 681 ms where M08-c362 saw 291-296 ms, and the deployment is a different one. With three runs per page over this link, the honest statement is that the live figures of this cycle measure the network path more than the site, and are not evidence of a regression in the code (the local build of the same commit scores 98-100).

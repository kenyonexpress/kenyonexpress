## 1. הארכיטקטורה

```
קורא
  │
  ├─ Upstash Redis (REST, בלי SDK)     ← עיקרי
  │      נכשל? נופל הלאה, לא זורק
  │
  ├─ Postgres check_rate_limit         ← גיבוי, service key בלבד
  │      נכשל? נופל הלאה
  │
  └─ backend: 'open' + log.error       ← שניהם מתו. §6.
```

### 1.1 למה ‏REST ולא ‏`@upstash/redis`

שתי סיבות שנמדדו, ואף אחת מהן אינה אסתטית:

1. **‏`node_modules` של worktree הוא symlink לצ'קאאוט הראשי.** ‏`pnpm add`
   שם היה כותב מחדש את ה-store שכל worktree חי אחר קורא ממנו.
2. **‏`src/proxy.ts` רץ ב-edge runtime תחת חלק מהפריסות, ול-edge אין ‏TCP
   sockets.** ‏`fetch` היא התחבורה היחידה ששני ה-runtimes חולקים.

**התוצאה: התלות ניתנת להחלפה בפונקציה אחת (`command()`).**

### 1.2 שני מפתחות, לא אחד

| ‏backend | מפתח | למה |
|---------|-------|-----|
| ‏Redis | ‏`rl:v1:<policy>:<id>` | ‏`rl:` מונע התנגשות; ‏`v1` מאפשר להחליף אלגוריתם בלי למגר מפתחות חיים |
| ‏Postgres | ‏`legacyRedisKey` | **המחרוזות כבר בטבלה בפרודקשן**, ושינוי שלהן מאפס מונים חיים |

**‏`v1` בתוך המפתח היא ההחלטה הטובה כאן:** מעבר מ-sorted set לחלון קבוע
משנה את **טיפוס הערך** באותו מפתח. הגרסה גורמת לקוד החדש פשוט להפסיק לקרוא
את הישנים, והם פגים לבד.

## 2. הטבלה: ‏33 מדיניויות

**המספרים לא הומצאו בקובץ.** כל שורה נקראה מאתר הקריאה שהחזיק אותה, ויש
טסט מלאי שנכשל אם קורא מעביר זוג שאינו בטבלה.

**לפני הקובץ:** ‏`5, 3600` הופיע ב-**‏8 אתרי קריאה בשלושה מודולים**,
ו-`120, 3600` ב-**ארבעה**, ואף מקום לא אמר אילו מהם אמורים להיות אותה מגבלה
ואילו רק התנגשו. "מה מגן על מסלול ה-OTP" חייב ‏grep.

### 2.1 אימות: המספרים הקטנים ביותר

| מדיניות | מגבלה | חלון | הסיבה |
|----------|--------|------|--------|
| `login` | 10 | שעה | ניחוש סיסמה, פר ‏IP |
| `login-account` | 20 | שעה | ניחוש על חשבון אחד מ-IP מתחלפים |
| `signup` | 5 | שעה | הצפת חשבונות |

## 3. תשובה לבריף: "‏public רופף, ‏admin הדוק"

**ההיררכיה הנכונה אינה לפי הרשאה. היא לפי מה שקורה כשהבקשה מצליחה:**

| מה הבקשה עושה | מגבלה | דוגמה |
|-----------------|--------|--------|
| **שולחת ‏SMS או מייל לאדם** | ‏**‏5/שעה** | ‏`phone-otp`, ‏`contact` |
| **מנחשת סוד** | ‏10-20/שעה | ‏`login`, ‏`staff-pin` |
| **נוגעת בכסף** | ‏10/דקה | ‏`begin_checkout` |
| **כותבת שורה זולה** | ‏60-120/שעה | ‏`cart_write` |
| **קוראת** | ‏120-300 | ‏`search` |

**קריאת אדמין (‏60) נדיבה יותר מטופס אנונימי (‏5), וזה נכון:** האדמין מזוהה,
מתועד, ולא עולה כסף. ‏**הרשאה גבוהה אינה סיבה למגבלה הדוקה.**

## 4. ההנחה שהשכבה כולה נשענת עליה

```ts
export async function getClientIp(): Promise<string> {
  const forwarded = headersList.get('x-forwarded-for')
  return forwarded?.split(',')[0]?.trim() ?? headersList.get('x-real-ip') ?? 'unknown'
}
```

**‏`x-forwarded-for` מגיע מהרשת, ושום דבר כאן לא מבחין בין ערך שהפלטפורמה
כתבה לבין ערך שהקורא הקליד.**

**נמדד מול האפליקציה הזו על localhost:** שלוש בקשות ל-`/api/search` עם שלושה
ערכי ‏`x-forwarded-for` שונים יצרו **שלוש שורות נפרדות ב-`rate_limits`**.

לכן, בלי ‏proxy מלפנים:

| הכיוון | התוצאה |
|---------|---------|
| התוקף כותב ‏IP מתחלף | **כל מגבלה מבוססת ‏IP היא אפס מגבלה** |
| התוקף כותב את ה-IP של אדם אחר | ‏**הוא מוציא את התקציב של האדם ההוא** |

**מה שמחזיק את זה: ‏Vercel כותבת את הכותרת בעצמה.**
זו **הנחה על הפריסה, לא תכונה של הקוד.**

**מה שלא היה עוזר:** להעדיף ‏`x-real-ip` או ‏`x-vercel-forwarded-for`. שתיהן
מגיעות באותו חוט ובדיוק באותה מידה ניתנות לזיוף בלי proxy. **סידור מחדש היה
מזיז את ההנחה, לא מסיר אותה.**

**אותה קריאה מופיעה בארבעה מקומות** (`api/a/route.ts`,
`api/app/session/route.ts`, ‏`vouchers/scan-context.ts`), ולכן שינוי אחד הוא
שינוי לארבעתם.

### 4.1 ההשלכה התפעולית

**‏אם האפליקציה תוגש אי פעם ממשהו שאינו כותב מחדש את הכותרת (‏Node חשוף,
‏reverse proxy לא מוגדר), כל המגבלות מבוססות ה-IP הן קישוט.**

זה שייך ל-`RUNBOOK.md` כתנאי פריסה, לא רק להערה בקוד.

## 5. ‏service key, וזו תכונת האבטחה

הפונקציות קראו בעבר ל-`createClient()`, הלקוח קשור-העוגייה, ולכן ה-RPC רץ
כ-`anon` או `authenticated`. ‏`check_rate_limit` דורש ‏EXECUTE לתפקיד שקורא
לו, **והמפתח הציבורי ציבורי בהגדרה.**

**כלומר: ההרשאה הזו הייתה נגישה לכל מי שיש לו טרמינל.**

היום הלימיטר רץ על ‏service key, וההרשאה בוטלה במיגרציה 145 שהוחלה.

## 6. מה קורה כששני ה-backends נופלים

```ts
log.error('rate_limit.open', { key, limit, windowSeconds })
return { allowed: true, backend: 'open' }
```

**המערכת נכשלת פתוח**, ורק אחרי ש-Upstash **וגם** Postgres שניהם לא זמינים.

### 6.1 האם זו ההחלטה הנכונה

**כן, ברוב המסלולים, ולא בכולם.**

| בעד פתוח | נגד |
|-----------|-----|
| ‏Postgres למטה = האתר למטה בלאו הכי | ‏`login` ו-`phone-otp` לא מוגנים בחלון הזה |
| כשל סגור על `refund-request` חוסם הודעה סטטוטורית | ‏`staff-pin` בלי מגבלה = ניחוש PIN חופשי |
| ‏`cart_write` סגור = חנות שבורה על תקלת רשת | - |

**המצב "פתוח" דורש ששני ה-backends ייפלו יחד, וזה תרחיש קצר וקיצוני.**

### 6.2 ההמלצה

**לא לשנות את ברירת המחדל.** במקום זה:

1. ‏**התראה על ‏`rate_limit.open`.** השורה הזו היא "העקבה היחידה שהבקשה לא
   נמדדה", ואף אחד לא מסתכל עליה היום. ‏`MONITORING-ALERTING.md`.
2. ‏**כשל סגור לשלוש מדיניויות בלבד:** ‏`login`, ‏`phone-otp-number`,
   ‏`staff-pin`. שלושתן מנחשות סוד או שולחות ‏SMS בתשלום, ואף אחת מהן אינה
   נתיב שמפיל את החנות אם ייחסם לדקה.

## 7. הפער האמיתי: אין ‏`Retry-After`

`429` מוחזר בלפחות שמונה מסלולים. ‏**אף אחד מהם לא שולח ‏`Retry-After`.**

```ts
return NextResponse.json({ ok: false, error: 'rate_limited' }, { status: 429 })
```

| מי נפגע | איך |
|----------|-----|
| **הלקוח** | "נסה שוב מאוחר יותר" בלי לומר מתי |
| **‏`apps/mobile`** | אין ‏backoff נכון; היא קורא שני למסלולים האלה |
| **‏crawler** | ‏Google מאט לפי ‏`Retry-After`; בלעדיו הוא מנחש |
| **‏k6** | לא מבחין בין ‏429 להאטה |

### 7.1 התיקון

‏`RateLimitDecision` **כבר מחזיר `resetAtMs`** מ-Upstash. ‏המידע קיים, הוא
פשוט לא נכתב לכותרת.

```ts
const retryAfter = Math.max(1, Math.ceil((decision.resetAtMs - Date.now()) / 1000))
return NextResponse.json(
  { ok: false, error: 'rate_limited' },
  { status: 429, headers: { 'Retry-After': String(retryAfter) } },
)
```

**‏`resetAtMs` הוא `null` בגיבוי ה-Postgres**, ואז נופלים ל-`windowSeconds`
כקירוב עליון. עדיף מכלום.

**עלות: שינוי בעוזר יחיד. תשואה: כל שמונת המסלולים, כולל האפליקציה.**
**זו הפעולה בעלת התשואה הגבוהה ביותר במסמך.**

## The one dirty load in pass 2

`/product/demo-flight` at 380, the eleventh of pass 2's 22 loads, at about
00:02:40 UTC. The HTML document itself answered 200 and the page rendered its
`<h1>` ("טיסה הלוך-חזור לאתונה"). Then every subresource still in flight
failed on the client side:

```
$ awk '/demo-flight @380/{p=1;print;next} /^\//{p=0} p' run2-prod.txt | sort | uniq -c   (abridged)
  10 console: Failed to load resource: net::ERR_NETWORK_CHANGED
  21 console: Failed to load resource: net::ERR_NAME_NOT_RESOLVED
   6 requestfailed: script net::ERR_NETWORK_CHANGED  .../_next/static/immutable/chunks/*.js
   3 requestfailed: font   net::ERR_NETWORK_CHANGED  .../_next/static/immutable/media/*.woff2
   1 requestfailed: other  net::ERR_NETWORK_CHANGED  .../_next/image?url=...
  14 requestfailed: script net::ERR_NAME_NOT_RESOLVED .../_next/static/immutable/chunks/*.js
   7 requestfailed: image  net::ERR_NAME_NOT_RESOLVED .../images/logo.webp, /_next/image?url=...
```

`ERR_NETWORK_CHANGED` is Chromium's own signal that the host's network
configuration changed while requests were open; `ERR_NAME_NOT_RESOLVED` for
`www.kenyonexpress.co.il`, a name that resolved for the ten loads before and
the eleven after, is the DNS path going away on the probing machine. No
response with a status code is involved (0 responses >= 400 in that load),
and the very next load, `/product/demo-flight` at 1440, is clean. The Mac's
unified log for 07:01:30 to 07:04:30 +07 returned nothing for `configd`,
`mDNSResponder`, `symptomsd`, `nehelper`, `wifid` or `airportd`, so the
corroboration is Chromium's error codes and the clean loads on either side.
The 6 broken images in that load are the 7 image requests that never
resolved. The 2 warnings in that load are the usual unused-preload notice
for `logo.webp` and `2x0yntgphzrdv.css`.

Pass 3, a full repeat on the same sample 25 seconds after pass 2 ended,
logs 0 errors on all 22 loads, including `/product/demo-flight` at 380.

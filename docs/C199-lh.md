## What was under 90 first, and why it was not the code

1. **Injected `Cookie` header (the C181 method): cart 87/74, checkout 96/87, account 94/67, and account 1440 Best Practices 96.** `--extra-headers` sends the session as a fixed request header. The browser's cookie jar stays empty, so a rotated session cookie from the server has nowhere to go. In the account 1440 trace, every `/account/*` prefetch from about 11.4 s on gets a 307 to `/login?next=...`, and Next's segment prefetch for that redirected URL answers 404. Those 404s are the nine console errors that cost Best Practices 4 points. With the same session put into the jar through CDP (`Storage.setCookies`), there were 0 console errors and Best Practices was 100 on all 54 jar runs in the three sets. Account 1440 went from 67 to 92-94. The proxy behaves correctly: an anonymous prefetch of a protected route is redirected to the sign-in page.
2. **TTFB of 1-2.5 s on whichever route runs first.** Every sub-90 jar run has TTFB > 1 s, and every run with TTFB around 350 ms scores 89-99. The slow route depends on run position, not on which route it is. In set A cart ran first and got 86/84. In set B checkout ran first and got the slow TTFB (2541 / 1761 / 1543 ms at 380) while cart scored 99/97. In the final set, one identical warm-up request before every run removed the effect for all three routes. The first request is slow because of the server's cold connection from this host (iPhone hotspot, Thailand) to Supabase eu-north-1. The `pnpm start` log shows `db.query_slow` on `auth:user` at 1.6-4.6 s, and curl to Supabase REST measured 0.92-15.1 s for one request during the runs. The only round trip on /cart is the `auth.getUser()` in `src/proxy.ts`. Replacing it with local JWT verification would change ban and revocation semantics to win a lab number. C181 declined that, and so does this item.
3. **SEO 92 on some account runs.** The failing audit is `robots-txt`: "Fetch of robots.txt failed: Timed out fetching resource". The same server answered `/robots.txt` 200 in 1-2 ms six times in a row by curl. This is Lighthouse's own fetch under page load, and the median holds at 100 in sets A and B.

Seen, not changed: the 404 in point 1 also shows in a real browser if the session ends while the user is on an `/account` page. It is console noise only; the next navigation still lands on `/login`.

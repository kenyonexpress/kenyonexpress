# M14-c366: Sentry release matches HEAD

Measured 06.11.2026, 16:39-16:42 +07, against production
`www.kenyonexpress.co.il`. Base HEAD `9ec92c46a`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c365.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `9ec92c46a11dfb00cd860e55fb6e24aeb3f5a51e`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first reading, taken while HEAD's build was running, did not match.**
HEAD was committed at 16:39:06 and its deployment was created at 16:39:14. At
16:39:55 the production alias still pointed at the previous deployment
(`c0a68f316`, one commit behind). At 16:40:31 the alias resolved to HEAD's
deployment, and the client chunks were fetched after that, between 16:41:08
and 16:41:50. That window exists after every push; it is the build time, not
a fault in the release wiring. The mismatched state was read from deployment
metadata only; the client chunk of the previous deployment was not fetched.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c365, M14-c364, M14-c363,
M14-c362, M14-c361, M14-c111 and BACKLOG #21. Events carry the right `release`
string, but Sentry has no release entity and no source maps, so production
stack traces stay minified. The fix is unchanged and is Ofir's: a new
`SENTRY_AUTH_TOKEN` in Vercel Production with the `project:releases` and
`org:read` scopes, created in the Sentry UI. The variable in Vercel is 51 days
old. That gap does not affect this item's check, which compares the tag
against HEAD.

The match is for `9ec92c46a`. The commit that records this item moves HEAD and
triggers a new production build, whose release will be that new SHA by the
same mechanism.

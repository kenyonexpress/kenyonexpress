## The local robots.txt timeout

`local-home-simulate-3` (07:17:02-07:17:21Z): `robots-txt` failed with "Fetch of robots.txt failed: Timed out fetching resource", SEO 92.

- `/robots.txt` is prerendered (`○` in the build route table, `x-nextjs-cache: HIT`). It still passes through `src/proxy.ts`, whose matcher excludes only `_next/static`, `_next/image`, `favicon.ico` and image extensions.
- The proxy awaits `lookupRedirect(pathname)` (`src/proxy.ts:125`). `src/lib/seo/redirects.ts` keeps the redirect table in memory for 5 minutes (`TTL_MS`); once it expires, the request that finds it expired awaits the reload from Supabase (`getMap`, lines 92-122) rather than being served from the old map.
- Timing fits: the server's first request was at about 07:12Z, the failed fetch about 5 minutes later. After the runs, a `curl` of `/robots.txt` at 07:25:36Z, the first local request in 7 minutes, took 3.36 s; the next 8 took 3-8 ms.

So the delay is one Supabase round trip from this machine over the VPN, paid by one request every 5 minutes. This was inferred from the code and the timing, not confirmed by instrumenting the proxy. On Vercel the same reload runs next to the database; its cost there was not measured. No live run failed `robots-txt` in this cycle (one did in c364).

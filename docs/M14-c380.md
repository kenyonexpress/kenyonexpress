# M14-c380: Sentry release matches HEAD

Measured 07.11.2026, 16:12-16:14 +07 (09:12-09:14 UTC), against production
`www.kenyonexpress.co.il`. Base HEAD `02ad3952a`. No code change.

## Result

**The release tag matches HEAD on every runtime. Unchanged since M14-c379.**
HEAD, the branch on origin and the deployment behind the production alias are
the same commit, `02ad3952aff8cfa957c81efec9cf121474c4e01e`, and the live
client bundle has that SHA baked in as its Sentry release.

**The first listing, taken while HEAD's build was running, showed the previous
deployment behind the alias.** HEAD was committed at 16:11:43 and its
deployment was created at 16:11:52. At 16:12:35 `vercel inspect` resolved the
alias to `dpl_AQ6NRzWBFx1LVyZNg13zGJFP5dcd` (`28aa390f9`, one commit behind)
and at 16:12:33 the listing showed HEAD's deployment `BUILDING`. HEAD's
deployment turned `READY` at 16:13:02 (deployment metadata) and the alias
resolved to it at 16:13:12. The client chunks were fetched after that, between
16:13:31 and 16:14:21. Same build window as M14-c373 through M14-c379, not a
fault in the release wiring.

**Sentry still has no release object for it.** The build's
`sentry-cli releases new` and the source-map upload both fail with
`Invalid token (http status: 401)`, as in M14-c361 through M14-c379, M14-c111
and BACKLOG #21. Events carry the right `release` string, but Sentry has no
release entity and no source maps, so production stack traces stay minified.
The fix is unchanged and is Ofir's: a new `SENTRY_AUTH_TOKEN` in Vercel
Production with the `project:releases` and `org:read` scopes, created in the
Sentry UI. The variable in Vercel is 52 days old. That gap does not affect
this item's check, which compares the tag against HEAD.

The match is for `02ad3952a`. The commit that records this item moves HEAD
and triggers a new production build, whose release will be that new SHA by
the same mechanism.
